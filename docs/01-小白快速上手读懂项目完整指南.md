## 三、宏观层面：整体业务、架构、模块、数据流

### 3.1 项目是什么（一句话版）

> **你用中文问"查询2026年销售额最高的商品"，系统自动翻译成 SQL → 去 MySQL 查数 → 再用中文告诉你结果，中间每一步实时推送到网页上。**

### 3.2 项目解决什么问题

**痛点**：业务同学想查数据但不会写 SQL → 提需求给数据同学 → 排期等待 → 来回沟通。

**方案**：让 AI 当"数据分析实习生"——听懂中文问题 → 查表结构 → 写 SQL → 审核安全 → 执行查询 → 汇报结果。

**安全边界**：
- 只读（永远不写库）
- 单查询（不允许多语句）
- 行数限制（默认最多 1000 行）
- 四层防线保证安全（后面详细讲）

### 3.5 数据流：一次请求的完整一生

以"查询2026年销售额最高的商品"为例，**数据在系统里怎么流转**：

```
用户在浏览器输入："查询2026年销售额最高的商品"
    │
    ▼ POST /api/chat/stream {question: "...", conversation_id: "abc"}
    │
    ▼ build_turn_input()
    │   读取 checkpointer 上一轮的状态（第一轮为空）
    │   组装 AgentState：{question, conversation_id, prev_question="", ...}
    │
    ▼ LangGraph 开跑 ─────────────────────────────────────
    │
    │  [节点 1] intent_node
    │  │  输入：question
    │  │  逻辑：关键词启发式（没有命中"你好/谢谢"等）→ LLM 分类
    │  │  输出：intent="DATA_QUERY", should_continue=True
    │  │  SSE 推送：event: thinking "正在理解问题..."
    │  │
    │  [节点 2] schema_recall_node
    │  │  输入：question
    │  │  逻辑：调用 KnowledgeRetriever.recall(question)
    │  │       → Chroma 向量检索 top-4 知识块
    │  │       → 分为 schema_text（表结构）和 evidence_text（业务规则）
    │  │  输出：retrieved_chunks=[...], schema_needs_tool=False
    │  │  SSE 推送：event: retrieval "检索Schema... 命中 3 条"
    │  │
    │  （如果 schema_needs_tool=True → 条件边绕进节点 2.5）
    │  [节点 2.5] tool_call_node（可选，不是每次都走）
    │  │  输入：question, retrieved_chunks
    │  │  逻辑：LLM bind_tools([search_schema, execute_sql])
    │  │       → LLM 决定调 search_schema("商品")
    │  │       → 执行工具，结果合并进 retrieved_chunks
    │  │  输出：tool_called=True, tool_results=[...]
    │  │  SSE 推送：event: tool "调用工具: search_schema"
    │  │
    │  [节点 3] sql_generate_node
    │  │  输入：question, retrieved_chunks, prev_question, prev_sql
    │  │  逻辑：组装 Prompt（方言+表结构+业务规则+问题+上一轮）
    │  │       → with_structured_output(SqlGeneration) 强制结构化
    │  │       → LLM 返回 {sql: "SELECT ...", reasoning: "..."}
    │  │  输出：generated_sql="SELECT p.name, SUM(...) ...", generated_reasoning="..."
    │  │  SSE 推送：event: sql "SELECT p.name, SUM(oi.amount)..."
    │  │
    │  [节点 4] sql_execute_node
    │  │  输入：generated_sql
    │  │  逻辑：sqlglot.validate_and_rewrite(sql)
    │  │       → AST 解析（只允许 SELECT）
    │  │       → 黑名单检查（禁止 INSERT/DELETE/DROP/...）
    │  │       → 危险函数检查（禁止 SLEEP/BENCHMARK）
    │  │       → 自动补 LIMIT 1000
    │  │       → aiomysql 只读账号执行
    │  │  输出：query_result=[{"name":"智能手机Pro","sales":9980}], row_count=1
    │  │  SSE 推送：event: result "查询完成, 共 1 行"
    │  │
    │  [节点 5] report_node
    │  │  输入：question, query_result, generated_sql
    │  │  逻辑：LLM 将行数据翻译成自然语言
    │  │  输出：final_answer="2026年销售额最高的商品是智能手机Pro..."
    │  │  SSE 推送：event: answer "2026年销售额最高的是..."
    │
    ▼ LangGraph 结束 ─────────────────────────────────────
    │
    ▼ SSE 推送：event: done [DONE]
    │
    ▼ 前端渲染时间线 + 高亮显示 answer
    │
    ▼ checkpointer 保存本轮完整 State（供下一轮使用）
```

### 3.7 关键设计原则（理解这些就理解了项目灵魂）

1. **LLM 做认知，代码做决策**
   - LLM 负责"读和写"（生成 SQL、总结结果、选择工具）
   - 流程由 LangGraph 图控制（走哪个节点由边决定，不是 LLM 决定）
   - 安全由代码保证（sqlglot 校验 + 只读账号，不指望 LLM 自觉）

2. **四层 SQL 安全纵深防御**
   - 第 1 层：Prompt 软约束（模板里写死"只准 SELECT"）
   - 第 2 层：结构化输出（Pydantic 强制格式）
   - 第 3 层：sqlglot AST 硬校验（解析语法树，禁止写操作）
   - 第 4 层：MySQL 只读账号（物理上只能 SELECT）

3. **离线可运行**
   - 无 API Key 时向量检索用本地哈希兜底
   - 测试用 helper 注入 + monkeypatch 绕过真实 LLM
   - 99 个测试全部离线通过

4. **单一事实来源**
   - `data/knowledge/*.md` 同时服务 RAG 检索和全量兜底
   - 改知识只改 md 文件，不需要改代码

## 四、中观层面：逐模块拆解与依赖关系

### 4.1 Agent 编排模块（`app/agent/`）— 全项目核心

**这个模块是整个项目的心脏。** 理解了它，就理解了 70% 的项目。

#### 4.1.1 state.py — 状态定义（数据骨架）

```python
# AgentState 是一个 TypedDict，所有节点共享
# 每个节点只改自己负责的字段，返回 partial dict

class AgentState(TypedDict):
    question: str                    # 用户问题（API 入口写入）
    conversation_id: str             # 会话 ID（API 入口写入）
    intent: str                      # "DATA_QUERY" 或 "CHAT"（intent_node 写入）
    should_continue: bool            # 是否继续（intent_node 写入）

    retrieved_chunks: list            # RAG 召回的知识块（schema_recall_node 写入）
    schema_needs_tool: bool           # 召回不足时 True，触发工具绕行

    tool_called: bool                 # 是否调用了工具（tool_call_node 写入）
    tool_results: list                # 工具执行结果（tool_call_node 写入）
    tool_error: str                   # 工具错误信息

    generated_sql: str                # LLM 生成的 SQL（sql_generate_node 写入）
    generated_reasoning: str          # LLM 的推理说明

    query_result: list                # SQL 执行结果（sql_execute_node 写入）
    row_count: int                    # 结果行数

    final_answer: str                 # 自然语言答案（report_node 写入）
    node_path: list                   # 经过的节点路径（每个节点追加）
    error: str                        # 错误信息（任意节点写入，不中断图）

    prev_question: str                # 上一轮问题（build_turn_input 写入）
    prev_sql: str                     # 上一轮 SQL
    prev_answer: str                  # 上一轮答案
```

**怎么读这个文件**：不要纠结 TypedDict 的语法。把它当成一个"数据合同"——每个节点的"写什么字段"都在这里声明了。

#### 4.1.2 nodes.py — 6 个节点函数（业务逻辑）

每个节点长这样：

```python
async def intent_node(state: AgentState) -> dict:
    # 1. 从 state 读需要的字段
    question = state["question"]

    # 2. 调用 helper 做业务（helper 是注入的，可替换）
    intent = await _intent_classifier(question)

    # 3. 返回"我要改的字段"（partial dict）
    return {
        "intent": intent,
        "should_continue": intent == "DATA_QUERY",
        "node_path": state.get("node_path", []) + ["intent"],
    }
```

**6 个节点速览**：

| 节点 | 输入字段 | 核心逻辑 | 输出字段 |
|---|---|---|---|
| `intent_node` | question | 关键词启发式 + LLM 分类 | intent, should_continue |
| `schema_recall_node` | question | Chroma 向量检索 top-4 知识块 | retrieved_chunks, schema_needs_tool |
| `tool_call_node` | question, retrieved_chunks | LLM bind_tools 决策 → 执行工具 | tool_called, tool_results |
| `sql_generate_node` | question, retrieved_chunks, prev_* | LLM + Prompt 模板 → 结构化 SQL | generated_sql, generated_reasoning |
| `sql_execute_node` | generated_sql | sqlglot 校验 → MySQL 执行 | query_result, row_count |
| `report_node` | question, query_result | LLM 总结成自然语言 | final_answer |

**关键设计：`set_helpers()` 机制**
- 节点不直接 import 具体实现，而是通过模块级变量调用 helper 函数
- `init_default_helpers()` 在启动时注入真实实现
- 测试时 `set_helpers(stub_functions)` 一键替换 → 99 个测试不需要真实 LLM

#### 4.1.3 graph.py — 图装配（节点连成图）

```python
# 图结构（线性 + 2 条条件边）

START → intent → schema_recall → [条件边] → sql_generate → sql_execute → report → END
                                      │
                                      └→ tool_call → sql_generate（绕行后回到主路）

# 条件边 1（intent 之后）：
#   intent == "CHAT" → 直达 report（跳过 SQL 流水线）
#   intent == "DATA_QUERY" → 继续 schema_recall

# 条件边 2（schema_recall 之后）：
#   schema_needs_tool == True 且 tool_called == False → 绕行 tool_call
#   否则 → 直接 sql_generate
```

**怎么读这个文件**：
1. 先看 `_build_state()` 函数 — 看节点怎么注册到图上
2. 再看两个条件边函数 `_route_after_intent()` 和 `_route_after_recall()`
3. 最后看 `get_compiled_graph()` — 编译 + 缓存 + checkpointer

#### 4.1.4 run_graph.py — 对外统一入口

- `build_turn_input()`：每轮入口，从 checkpointer 读上一轮状态，注入 `prev_*` 字段，**重置工具标志位**（防跨轮状态残留）
- `run_question()`：组装 input → 调用 `get_compiled_graph().ainvoke()` → 返回 `GraphRunResult`

### 4.2 RAG 模块（`app/rag/`）— 知识检索

**这个模块解决的问题**：表结构太多塞不进 Prompt → 用向量检索只取最相关的几块。

```
data/knowledge/*.md（知识原文）
    │
    ▼ documents.py: load_knowledge_chunks()
    │   按 ## 标题切片 → KnowledgeChunk(type=schema|business)
    │
    ▼ vector_store.py: ensure_indexed()
    │   文本 → Embedding 向量 → 存入 Chroma
    │   无 API Key 时用 _HashEmbedding（本地哈希）兜底
    │
    ▼ retriever.py: recall(question)
    │   问题 → Embedding → Chroma top-K 检索
    │   结果按 type 分成 schema_text 和 evidence_text
    │
    ▼ 注入到 SQL 生成的 Prompt 槽位
```

**关键文件速读顺序**：
1. `documents.py` — 知识怎么切片的（按 H2 标题）
2. `vector_store.py` — 向量库怎么存和查的
3. `retriever.py` — 检索器怎么把结果分成两个槽位的

### 4.3 SQL 安全模块（`app/security/sql_validator.py`）— 四层防线

**这是面试高频考点。** 读这个文件时画一个表格：

| 检查项 | 怎么做 | 被拦截的例子 |
|---|---|---|
| 空 SQL | 字符串检查 | `""` |
| 多语句 | 检查分号 | `SELECT 1; DROP TABLE users` |
| 顶层白名单 | AST 解析，只认 `exp.Select` | `DELETE FROM users` → Delete 节点 |
| 全树黑名单 | 遍历 AST，禁止写操作节点 | `SELECT * FROM (DELETE ...)` 子查询藏写操作 |
| 危险函数 | 函数名黑名单 | `SELECT SLEEP(100)` |
| 自动补 LIMIT | AST 里没有 limit 节点就注入 | `SELECT * FROM users` → `SELECT * FROM users LIMIT 1000` |

### 4.4 工具模块（`app/tools/`）— Tool Calling

两个工具：

| 工具 | 函数签名 | 干什么 | 返回什么 |
|---|---|---|---|
| `search_schema` | `search_schema(keyword: str)` | 按关键词检索知识库 | `{keyword, count, chunks: [...]}` |
| `execute_sql` | `execute_sql(sql: str)` | 校验并执行 SQL | `{error, row_count, rows, total_rows, truncated}` |

**关键设计**：
- 工具用 `@tool` 装饰器标注，docstring 就是给 LLM 看的"说明书"
- `execute_sql` 内部强制走 sqlglot 校验 — **校验在建立数据库连接之前**
- 工具返回 JSON（不是抛异常），让 LLM 能读到错误信息并调整
- `MAX_TOOL_CALLS_PER_TURN = 3`，限制每轮最多 3 次工具调用

**读什么**：四道安全检查的具体实现。

**读法**：
1. `ALLOWED_ROOT_TYPES` — 顶层白名单（只允许 `exp.Select`）
2. `FORBIDDEN_NODE_TYPES` — 全树黑名单（INSERT/DELETE/DROP/ALTER/...）

**关键理解**：为什么用 AST 而不是字符串匹配？

### 5.3 跳过冗余代码的技巧

**可以跳过的代码**：
| 代码类型 | 为什么可以跳 | 举例 |

## 七、常见坑点与避坑建议

### 坑 1：一上来就读源码，不看 README

**症状**：打开 `nodes.py` 直接看，完全看不懂在干什么。

**原因**：没有先建立"这个项目做什么"的全局认知。

**避坑**：先花 10 分钟读 README，再花 5 分钟看目录结构，再花 10 分钟跑起来项目在浏览器问一个问题。**有了感性认识再读代码**。

### 坑 2：不理解 TypedDict 就纠结语法

**症状**：看到 `class AgentState(TypedDict):` 就卡住。

**避坑**：TypedDict 就是"一个 dict，但声明了它有哪些 key 和 value 类型"。把它当成 JSON Schema 理解即可，不需要纠结 Python 类型系统。

### 坑 3：不知道 LangGraph 是什么就硬读 graph.py

**症状**：看到 `StateGraph`、`add_node`、`add_conditional_edges` 完全不知所云。

**避坑**：花 10 分钟看 LangGraph 官方文档的 Quickstart。核心概念就 4 个：
- **State**：所有节点共享的 dict
- **Node**：`async def(state) -> dict` 的函数
- **Edge**：节点之间的连接（固定下一跳）
- **Conditional Edge**：根据 state 内容决定走哪条路

### 坑 4：把 LangGraph 和 LangChain 混为一谈

**症状**：搞不清两者的关系。

**避坑**：
- **LangChain**：提供 LLM 调用、Prompt 模板、工具封装等基础能力
- **LangGraph**：在 LangChain 之上，提供流程编排（State/Node/Edge/条件边/Checkpointer）
- 关系：LangGraph 依赖 LangChain，但它们解决不同层面的问题

### 坑 5：不理解"helper 注入"就看 nodes.py

**症状**：看到 `_intent_classifier`、`_schema_recaller` 等模块级变量，找不到它们在哪定义的。

**避坑**：
- 这些是**模块级变量**，初始值为 None
- `init_default_helpers()` 在 `graph.py` 里把真实实现注入进去
- 测试时 `set_helpers(stub)` 替换成假实现
- 这是**依赖注入**模式，不是直接 import

### 坑 6：以为 SSE 需要额外部署服务

**症状**：到处找 SSE 服务器配置。

**避坑**：SSE 就是 HTTP 响应的一种格式，FastAPI 的 `StreamingResponse` 直接支持。格式就是 `event: xxx\ndata: yyy\n\n`。

### 坑 7：把 checkpointer 当成数据库

**症状**：以为多轮对话需要建一张"会话表"存历史。

**避坑**：
- `MemorySaver` 是**内存实现**，不需要数据库
- 它按 `thread_id`（本项目用 `conversation_id`）存每轮的完整 State
- 重启后丢失是预期行为，生产环境换成持久化实现即可

### 坑 8：不理解"为什么不用字符串匹配检查 SQL 安全"

**症状**：看到 sqlglot AST 校验觉得"为什么不直接 `if "DELETE" in sql: reject`"。

**避坑**：
- 字符串匹配会被注释绕过：`DELETE/**/FROM` 字符串里确实有 DELETE 但 SQL 语义可能不同
- 字符串匹配被大小写绕过：`delete` vs `DELETE`
- 字符串匹配被编码绕过
- AST 解析后 `DELETE` 一定是 `Delete` 节点，无论怎么变形都藏不住
- 而且 AST 解析失败本身就是拒绝理由（解析不了的 SQL 更不能执行）

### 坑 9：不理解"为什么 RAG 召回不了就走 tool_call"

**症状**：条件边绕行逻辑看起来多余。

**避坑**：
- 如果 RAG 召回 0 条 schema 知识 → LLM 生成 SQL 必然编造表名（幻觉）
- 所以让 LLM 自己决定用什么关键词再查一次（search_schema 工具）
- 工具也查不到 → 还有全量知识文档兜底
- 这是"三级兜底"设计：RAG → 工具检索 → 全量文档

### 坑 10：读测试时不知道 stub 怎么工作

**症状**：看到 `conftest.py` 里的 `_StubChat`、`_StubT2S`、`_StubRetriever` 不知道在干什么。

**避坑**：
- 这些是**假实现**，让测试不需要真实 LLM/数据库就能跑
- 原理：`set_helpers(stub_function)` 把节点的 helper 替换成假的
- 假实现返回固定值（如固定 SQL "SELECT 1"），测试验证的是"编排逻辑"而非"LLM 质量"

### 坑 11：跨轮状态残留

**症状**：第二轮工具路径永远不触发。

**原因**：checkpointer 会把上一轮的 `tool_called=True` 带进本轮，条件边判定 `tool_called == False` 永远不成立。

**避坑**：`build_turn_input()` 在每轮入口**显式重置**工具标志位。这是真实踩过的坑。

### 坑 12：以为项目需要 GPU 或本地模型

**症状**：犹豫要不要装 PyTorch 或下载模型权重。

**避坑**：这个项目**不跑本地模型**。所有 LLM 调用都是远程 API（OpenAI 兼容协议）。没有 GPU、没有 PyTorch、没有模型权重下载。
