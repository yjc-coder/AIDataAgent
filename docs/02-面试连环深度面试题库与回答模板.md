## 一、基础入门提问（验证是否真的参与过）

> 目标：快速筛选——候选人是否真的做过这个项目，还是照着教程跑了一遍。

### A. 项目总览

**Q A1. 用 1 分钟介绍一下这个项目，它是做什么的？**

**回答**：
"这是一个面向业务数据库的 AI 数据分析 Agent。用户用中文问'2026年销售额最高的商品是什么'，系统自动完成意图判断、RAG 检索表结构和业务规则、LLM 生成 SQL、sqlglot 校验后用只读账号执行 MySQL，最后把结果总结成自然语言，全过程通过 SSE 实时推送。技术栈是 FastAPI + LangChain + LangGraph + Chroma + sqlglot + MySQL。我的设计原则是'LLM 做认知、代码做决策'——流程由 6 个节点的 LangGraph 图掌控，LLM 只在节点内生成内容，保证可控可测试。目前 99 个单元测试全部离线通过。"

> **代码锚点**：README「核心流程」、`app/agent/graph.py`

**追问 A1-1. 项目的核心业务场景是什么？解决什么痛点？**

**回答**："核心业务场景是让不会写 SQL 的业务同学用自然语言自助查数。痛点是：业务提需求→数据同学写 SQL→排期等待，沟通成本高。"

**追问 A1-2. 用户群体是谁？典型使用流程是怎样的？**

**回答**："用户群体是产品经理、运营等业务同学。典型流程：打开网页输入中文问题→看 Agent 逐步执行（理解→检索→生成SQL→查询→回答）→拿到自然语言答案。"

**追问 A1-3. 项目的技术栈有哪些？为什么选这些？**

**回答**："技术栈：FastAPI（Web 框架，原生异步）、LangChain（LLM 调用/Prompt/工具）、LangGraph（流程编排）、Chroma（向量库，嵌入式）、sqlglot（SQL AST 安全校验）、aiomysql（异步 MySQL 连接池）。选这些是因为全异步链路无阻塞、每个组件解决一个明确问题。"

**追问 A1-4. 代码量大概多少？测试有多少个？你负责哪些部分？**

**回答**："代码约 X 千行（不含测试），测试 99 个用例。核心设计决策都是我做的：图结构怎么定、条件边放在哪、四层防线怎么排布、工具返回 JSON 让节点回灌 state 的设计、离线测试的 helper 注入模式。我可以对任何一个文件的任何一行做解释。"

**追问 A1-5. 这个项目和你的另一个 Java 高并发项目有什么关系？为什么做两个不同方向的项目？**

**回答**："两个项目刻意互补。Java 项目证明高并发后端能力（Spring Boot + Redis + RabbitMQ + 秒杀）；这个项目证明 AI 应用工程化能力。两者的共同点：都是'把不可靠的外部依赖（下游服务/LLM）用工程手段变可靠'——Java 里是限流熔断兜底，这里是从容校验和多层防线。"

### B. 请求链路

**Q B1. 用户在浏览器输入"查询2026年销售额最高的商品"到看到结果，中间经过哪些步骤？**

**回答**：
"前端 fetch POST /api/chat/stream，body 里带 question + conversation_id。FastAPI 调 build_turn_input() 从 checkpointer 读上一轮状态（第一轮为空），然后 LangGraph 开跑 6 个节点：intent（判定 DATA_QUERY）→ schema_recall（Chroma 向量检索 top-4 知识块）→ [可选 tool_call 绕行] → sql_generate（LLM 结构化输出生成 SQL）→ sql_execute（sqlglot 校验 + 只读账号执行）→ report（LLM 总结成自然语言）。每个节点执行完推一条 SSE 事件，前端渲染时间线。"

**追问 B1-1. 前端发的是什么请求？什么方法？什么路径？**

**回答**："POST /api/chat/stream，Content-Type: application/json，body 是 {question, conversation_id}。"

**追问 B1-2. 请求到了后端，第一个被调用的函数是什么？**

**回答**："第一个被调用的是 app/agent/run_graph.py 的 build_turn_input()，它组装 AgentState 后调 run_question()。"

**追问 B1-3. LangGraph 图有几个节点？分别是什么？**

**回答**："6 个节点：intent、schema_recall、tool_call（可选）、sql_generate、sql_execute、report。都在 app/agent/nodes.py 里，每个是 async def(state) -> dict 纯函数。"

**追问 B1-4. 两个条件边分别在哪个节点之后？什么条件触发？**

**回答**："条件边 1 在 intent 之后：intent==CHAT 直达 report 跳过 SQL 流水线。条件边 2 在 schema_recall 之后：schema_needs_tool 且 tool_called==False 时绕行 tool_call，否则直接 sql_generate。"

**追问 B1-5. 最后结果怎么返回给前端的？SSE 事件的顺序是什么？**

**回答**："SSE 事件顺序：thinking → retrieval → [可选 tool] → sql → result → answer → done。每帧格式是 event: xxx\\ndata: yyy\\n\\n。"

**追问 B1-6. 如果是闲聊（比如"你好"），流程会怎么走？跳过哪些节点？**

**回答**："闲聊走条件边 1：intent==CHAT → 直达 report 节点，跳过 schema_recall、tool_call、sql_generate、sql_execute 四个节点。report 里 LLM 直接回答闲聊。"

> **代码锚点**：`app/api/stream.py`、`app/agent/graph.py:_build_state`

### C. 关键文件

**Q C1. 你觉得这个项目最重要的 3 个文件是哪些？为什么？**

**回答**：
"第一是 app/agent/state.py——AgentState 定义了所有节点共享的数据字段，是全项目数据流的骨架。第二是 app/agent/nodes.py——6 个节点函数各改哪几个字段，是业务逻辑的核心。第三是 app/security/sql_validator.py——四层安全防线，面试最高频考点。"

**追问 C1-1. `app/agent/state.py` 里 AgentState 有哪些关键字段？**

**回答**："AgentState 关键字段：question、intent（DATA_QUERY/CHAT）、retrieved_chunks、schema_needs_tool、tool_called、generated_sql、generated_reasoning、query_result、row_count、final_answer、node_path、error、prev_question/prev_sql/prev_answer。"

**追问 C1-2. `app/agent/nodes.py` 里有几个节点函数？每个节点改哪些 state 字段？**

**回答**："6 个节点函数：intent_node 写 intent/should_continue；schema_recall_node 写 retrieved_chunks/schema_needs_tool；tool_call_node 写 tool_called/tool_results；sql_generate_node 写 generated_sql/generated_reasoning；sql_execute_node 写 query_result/row_count；report_node 写 final_answer。每个节点都追加 node_path。"

**追问 C1-3. `app/security/sql_validator.py` 做了哪几层校验？**

**回答**："sql_validator.py 做了四层校验：空 SQL 检查、多语句检查、sqlglot AST 解析（顶层白名单只认 SELECT、全树黑名单禁止写操作节点）、危险函数黑名单（SLEEP/BENCHMARK/LOAD_FILE）、自动补 LIMIT 1000。"

**追问 C1-4. `app/agent/graph.py` 里两条条件边的判定条件是什么？**

**回答**："条件边 1 判定：intent == 'CHAT'。条件边 2 判定：schema_needs_tool == True and tool_called == False。"

**追问 C1-5. `app/agent/run_graph.py` 的 `build_turn_input()` 做了什么事？**

**回答**："build_turn_input() 做三件事：① 从 checkpointer 用 aget_state 读上一轮的 question/SQL/answer 作为 prev_*；② 重置工具标志位（tool_called=False、schema_needs_tool=False、tool_results=[]、tool_error=''）；③ 组装 AgentState。"

> **代码锚点**：`app/agent/state.py`、`app/agent/nodes.py`、`app/security/sql_validator.py`

### D. 运行方式

**Q D1. 这个项目怎么跑起来？有几种方式？**

**回答**：
"三种：A 有真实 API Key 全功能模式——docker compose up -d mysql 起数据库、pip install 装依赖、python data/seed_data.py 灌数据、uvicorn 启动。B 无 Key 离线模式——跳过 API Key 配置，向量检索用本地哈希兜底，pytest 全部可跑。C Docker 一键全栈——docker compose up -d --build。"

**追问 D1-1. 没有 API Key 的情况下能跑吗？怎么跑的？**

**回答**："没有 API Key 能跑。占位 key 调真实 LLM 返回 401（预期行为，说明链路通）。向量检索用 _HashEmbedding 本地兜底，整条流水线结构可运行可测试。"

**追问 D1-2. 离线模式下哪些功能不工作？哪些仍然工作？**

**回答**："离线模式不工作的：真实 LLM 对话（返回 401）、真实 Embedding 向量化（降级为哈希）。仍然工作的：pytest 99 passed、向量检索结构（哈希相似度）、sqlglot 校验、图路由、SSE 结构。"

**追问 D1-3. Docker 方式启动后，MySQL 的两个账号分别是什么权限？为什么需要两个？**

**回答**："Docker 启动后两个 MySQL 账号：root（管理员，用于灌种子数据）和 readonly（应用运行时用，仅 SELECT 权限）。两个账号是因为纵深防御——应用代码用 readonly，即使代码全被绕过也写不了库。"

**追问 D1-4. 怎么灌入种子数据？种子数据有多少条？**

**回答**："灌种子数据用 python data/seed_data.py，连 MySQL 后 TRUNCATE 再插入。数据规模：约 200 用户、8 分类、约 60 商品、约 2000 订单、约 4958 订单明细。时间范围 2024-2026，订单状态权重 paid 80%/refunded 10%/cancelled 10%。"

**追问 D1-5. 测试怎么跑？`pytest` 运行后期望什么结果？为什么有些 skipped？**

**回答**："pytest 运行后期望 99 passed, 5 skipped。5 个 skipped 是需要真 MySQL 的冒烟用例，连不上库自动 skip 不 fail，CI 友好。连上 MySQL 后这 5 个自动启用。"

> **代码锚点**：`.env.example`、`docker-compose.yml`、`data/seed_data.py`、`pytest.ini`

### E. 项目产出

**Q E1. 项目的 99 个测试都测了什么？你怎么做到离线测试 LLM 应用的？**

**回答**：
"核心机制是依赖注入 + 模块引用 monkeypatch。五个节点 helper 通过 set_helpers 注入，测试传 stub。于是 99 个测试覆盖：sqlglot 校验全行为矩阵、RAG 切片/检索/内容守卫、6 节点单元行为、图级路由、多轮注入与会话隔离、SSE 事件顺序、API 契约。stub 掉 LLM 测的是我的编排逻辑——LLM 正确性我控制不了，但我能控制'LLM 返回垃圾时系统是否优雅降级'。"

**追问 E1-1. `conftest.py` 里有哪些 fixture？它们的作用是什么？**

**回答**："conftest.py 里有三类关键 fixture：Stub LLM（_StubChat，用于测原始 LLM 调用链路）、Stub Text2SqlGenerator（_StubT2S，返回固定 SQL 和 reasoning，绕过真实 LLM 和 RAG）、Stub Retriever（_StubRetriever，返回固定 chunks，避免真实嵌入 API）。还有 db_ready fixture 检测 MySQL 可达性。"

**追问 E1-2. `_StubChat`、`_StubT2S`、`_StubRetriever` 分别是什么？怎么工作的？**

**回答**："_StubChat 是 ChatModel 的假实现，返回固定 AIMessage。_StubT2S 是 Text2SqlGenerator 的假实现，agenerate() 直接返回 Text2SqlResult(sql='SELECT 1', reasoning='stub', chunks=[...])。_StubRetriever 的 recall() 返回固定 RecallResult。它们都通过 set_helpers() 注入到 nodes.py 的模块级变量。"

**追问 E1-3. 为什么需要 stub 掉 LLM 还能测出有价值的的东西？**

**回答**："需要 stub 掉 LLM 才能测出有价值的东西：编排逻辑（节点顺序对不对、条件边路由对不对）、降级行为（LLM 返回空时系统是否优雅处理）、安全防线（sqlglot 拦截是否生效）、状态流转（AgentState 字段谁写谁读对不对）。这些是工程能力的体现，不依赖 LLM 质量。"

**追问 E1-4. 5 个 skipped 的测试是什么？为什么跳过？什么条件下会运行？**

**回答**："5 个 skipped 是需要真 MySQL 的冒烟用例——比如真实执行 SQL 查询返回数据的端到端测试。db_ready fixture 检测连不上就 skip。连上库自动启用，因为校验在建立连接之前，不需要 LLM 也能跑。"

> **代码锚点**：`tests/conftest.py`、`tests/test_tools.py`、`tests/test_stream.py`

> 目标：验证候选人对业务需求、流程边界的理解深度。

### F. 业务场景与需求

**Q F1. 这个项目的业务场景是什么？谁会用它？替代了什么工作流程？**

**回答**：
"目标是'让不会写 SQL 的业务同学安全地自助查数'，替代的场景是：业务提需求→数据同学写 SQL→排期等待。安全的可用性边界很清楚：只读、单查询、LIMIT 保护，天然适合公司内部 BI 助手形态。"

**追问 F1-1. 业务同学的痛点是什么？为什么要用 AI 而不是教他们写 SQL？**

**回答**："业务同学的痛点是不会写 SQL，每次查数都要提需求给数据团队排期。用 AI 而不是教 SQL 是因为：SQL 学习门槛高、表结构复杂业务同学搞不清 JOIN 路径、口径不同写出来结果不对。AI 知道表结构和业务规则，自动处理这些。"

**追问 F1-2. 为什么不直接用 BI 工具（如 Metabase / Superset）？**

**回答**："BI 工具需要用户自己拖拽维度度量、理解表关系。对于'就问一句话要答案'的场景，自然语言交互比拖拽报表直观得多。BI 工具适合固定看板，这个系统适合即时探索性查询。"

**追问 F1-3. 这个系统和传统报表系统的区别是什么？**

**回答**："传统报表系统是预定义看板，用户只能看已配好的图表。这个系统是即时查询，用户问什么就查什么，灵活但单次查询粒度。两者互补不是替代。"

**追问 F1-4. 有没有考虑过接入权限控制？不同用户只能看自己部门的数据怎么办？**

**回答**："权限控制是明确的生产化改进项。当前设计预案：在 SQL 生成层注入用户权限信息（如 department_id），Prompt 里加规则'WHERE 必须包含 department_id = 用户的部门'，sqlglot 可以检查 SQL 是否包含权限过滤条件。"

**追问 F1-5. 如果业务用户问了超出数据库范围的问题（比如问外部数据），系统怎么处理？**

**回答**："超出数据库范围的问题：intent_node 判定为 DATA_QUERY 后走 SQL 流水线，但 sql_generate 时 LLM 发现 schema 里没有相关表，生成的 SQL 会执行失败或返回空。系统不会假装知道外部数据，会返回错误信息提示'当前数据库无法回答此问题'。"

> **代码锚点**：README、`app/agent/nodes.py:intent_node`

### G. 业务边界

**Q G1. 这个系统只做只读查询，为什么不做写操作（插入/更新）？**

**回答**：
"只做只读是因为安全边界：只读、单查询、LIMIT 保护。写操作的风险是数据损坏、数据泄露、不可逆操作。AI 生成的 SQL 即使有安全校验，写操作的风险面也比读操作大一个数量级。"

**追问 G1-1. 如果产品要求加"写操作"功能，你会怎么设计？安全边界在哪？**

**回答**："如果产品要求加写操作，我会设计三层：① 写操作用独立工具（不是 execute_sql），有独立的审批流程；② sqlglot 校验只允许特定表的 INSERT/UPDATE，WHERE 条件必须包含主键；③ 数据库账号分读写权限，写操作用独立连接池。安全边界在'哪些表可写、什么条件下可写'。"

**追问 G1-2. 只读限制在代码里怎么保证的？有几层防线？**

**回答**："只读限制在代码里有四层防线：Prompt 软约束（模板写'只准 SELECT'）、结构化输出（Pydantic 格式约束）、sqlglot AST 硬校验（顶层只认 SELECT）、MySQL readonly 账号（物理上只能 SELECT）。"

**追问 G1-3. 如果 LLM 被诱导生成了 `DELETE FROM orders`，这个 SQL 会执行吗？在哪一层被拦截？**

**回答**："如果 LLM 被诱导生成 DELETE FROM orders：第 1 层 Prompt 可能拦不住（LLM 被诱导），第 2 层结构化输出保证输出格式正确但不保证语义，第 3 层 sqlglot 解析出 Delete 节点，在 FORBIDDEN_NODE_TYPES 黑名单里直接拒绝——这发生在建立数据库连接之前。即使前 3 层全被绕过，第 4 层 readonly 账号物理上无 DELETE 权限。"

**追问 G1-4. 只读限制是"没有写功能"还是"有写功能但被禁止"？这个区别有什么意义？**

**回答**："是'没有写功能'而不是'有写功能但被禁止'。execute_sql 工具内部调 run_select，run_select 调 validate_and_rewrite 做安全校验然后执行——整个链路里根本没有写操作的代码路径。区别在于攻击面：'禁止'意味着有写功能存在可以被绕过，'没有'意味着绕过校验也找不到写代码。"

> **代码锚点**：`app/security/sql_validator.py`、`app/tools/execute_sql.py`、`docker-compose.yml`

### H. 知识库与业务规则

**Q H1. 知识库里的业务规则是怎么定义的？在哪里？**

**回答**：
"知识库在 data/knowledge/ 目录下，分 schema/ 和 business/ 两个子目录。schema/ecommerce.md 是 5 张表的字段说明 + JOIN 模板。business/sales.md 定义销售额规则，business/refund.md 定义退款规则。都是 markdown，按 ## 标题分块，同时服务 RAG 检索和全量兜底。"

**追问 H1-1. `data/knowledge/business/sales.md` 里定义了哪些业务规则？**

**回答**："sales.md 定义的核心规则：销售额 = SUM(order_items.amount)，单位人民币元，仅统计 orders.status='paid' 的订单。时间维度用 WHERE YEAR(o.created_at) = X。还包含商品维度（模糊匹配、分类筛选）、用户维度（城市筛选）、高频模板（按商品/城市/月聚合）。"

**追问 H1-2. "销售额"的定义是什么？为什么只统计 `paid` 状态的订单？**

**回答**："销售额只统计 paid 是因为业务定义：paid 表示已完成的有效订单，refunded（退款）和 cancelled（取消）不计入。这是业务口径不是技术决策。refund.md 里明确写了'有效订单 = paid'。"

**追问 H1-3. 退款和取消的订单怎么处理？退款率怎么算？**

**回答**："退款和取消：refund.md 定义 orders.status='refunded' 不计入销售额，退款率 = refunded_count / paid_count。cancelled 也不计入，可以和 refunded 合并统计非有效订单。"

**追问 H1-4. 如果业务规则变更了（比如"取消的订单也算销售额"），需要改哪里？改代码还是改知识库？**

**回答**："业务规则变更只改 md 文件，不需要改代码。比如'取消也算销售额'：改 refund.md 里的规则描述，重启后 RAG 自动重建索引，LLM 生成的 SQL 就会包含 cancelled。这就是'单一事实来源'的好处——知识是数据不是代码。"

**追问 H1-5. 知识库的 md 文件同时服务于 RAG 和全量兜底，这个"单一事实来源"设计有什么好处？**

**回答**："单一事实来源的好处：① 改知识只改 md 不改代码，降低出错风险；② RAG 和全量兜底读同一个文件，不会出现'RAG 版本和兜底版本不一致'；③ 知识可审查——md 文件就是业务规则的完整文档。"

> **代码锚点**：`data/knowledge/business/sales.md`、`data/knowledge/business/refund.md`、`data/knowledge/schema/ecommerce.md`

### I. 多轮对话的业务逻辑

**Q I1. 用户第一轮问"查询2026年销售额最高的商品"，第二轮问"那2025年呢"，系统怎么理解"那"？**

**回答**：
"每轮入口 build_turn_input() 用 aget_state 从 checkpointer 读上一轮的 question、SQL、final_answer，作为 prev_* 写进本轮 state。sql_generate 节点把它们格式化进 Prompt 的 PREVIOUS_STEPS 槽，并附一句'如有"那/它"等指代，基于上一轮消解'。于是'那2025年呢'在 LLM 眼里实际是：当前问题 + 上轮问题'查询2026年销售额最高的商品' + 上轮 SQL——指代自然消解。"

**追问 I1-1. 多轮对话的上下文怎么传递的？存在哪里？**

**回答**："上下文传递通过 checkpointer（MemorySaver）按 conversation_id 存储每轮完整 State 快照。build_turn_input() 用 aget_state 读上一轮，注入 prev_question/prev_sql/prev_answer。"

**追问 I1-2. 为什么只带上一轮而不是全量历史？**

**回答**："只带上一轮因为 Text-to-SQL 的指代链很短——通常就是'上一轮问的什么'。全量历史徒增 token 且引入远距离干扰。存储和上下文解耦：checkpointer 存全量 State 快照，Prompt 只带最近一轮。"

**追问 I1-3. 如果用户问"那前年呢"（跨三轮引用），能理解吗？为什么？**

**回答**："跨三轮引用当前不支持，因为 build_turn_input 只读一轮。要支持只需改读取深度——读两轮甚至三轮的 State。存储层不用动，因为 checkpointer 存了全量快照。"

**追问 I1-4. 如果第一轮就问"那2025年呢"（没有前文），系统怎么处理？**

**回答**："第一轮就问'那2025年呢'：prev_* 全为空，PREVIOUS_STEPS 槽是 (none)，LLM 没有指代对象。合理行为是反问澄清。做指代缺失检测（规则判断'那/呢'出现在首轮就主动反问）是个不错的增强，在改进清单里。"

**追问 I1-5. 多轮对话的会话隔离怎么保证？A 的上下文不会泄露给 B？**

**回答**："会话隔离由 checkpointer 的 thread_id 保证，我用 conversation_id 作 thread_id。不同 conversation_id 读不同快照。有专门测试 test_different_conversations_do_not_leak_context 验证：会话 A 问完销售额，会话 B 直接问'那2025年呢'，断言 B 的 Prompt 里 prev 是 (none)。"

> **代码锚点**：`app/agent/run_graph.py:build_turn_input`、`app/agent/nodes.py:_format_prev_steps`、`tests/test_multi_turn.py`

### J. 整体架构

**Q J1. 画出（或口述）这个项目的架构图，从浏览器到数据库。**

**回答**：
"五层：浏览器（Vue3 SSE 时间线）→ FastAPI（4 个 HTTP 端点）→ run_graph.py（统一入口，多轮上下文注入）→ agent/（LangGraph 图：6 节点 + 2 条件边）→ 能力层（rag/ 检索、tools/ 工具、text2sql.py 生成、security/ 校验）→ 基础设施（llm/、database/、config.py）。"

**追问 J1-1. 分几层？每层的职责是什么？**

**回答**："五层：API 层（HTTP 端点）、Agent 编排层（LangGraph 图）、能力层（RAG/Tools/SQL生成/SQL安全）、基础设施层（LLM 客户端/数据库连接池/配置）、数据层（MySQL/Chroma/知识库 md 文件）。"

**追问 J1-2. API 层和 Agent 层怎么解耦的？解耦的机制是什么？**

**回答**："解耦机制是 set_helpers 注入：节点不直接 import 具体实现，而是通过模块级变量调用 helper 函数。init_default_helpers() 在启动时注入真实实现，测试时 set_helpers(stub) 一键替换。所以测试可以整体替换任何一环。"

**追问 J1-3. 如果去掉 LangGraph 自己写流程编排，可行吗？代价是什么？**

**回答**："去掉 LangGraph 技术上可行，但条件边路由、checkpointer 状态持久化、astream 流式输出都要手写。LangGraph 用确定性的数据结构把流程表达出来，还免费给了 /api/graph/structure 图结构自省能力。代价是手写这些可能出 bug，LangGraph 已经验证过。"

**追问 J1-4. 为什么 API 层不直接调 LLM 生成 SQL，而是要走 6 个节点？**

**回答**："API 层不直接调 LLM 是因为：意图需要先判断（闲聊不走 SQL）、知识需要先检索（控制上下文）、SQL 需要先校验（安全）、结果需要总结（自然语言）。这些步骤有顺序依赖和条件分支，不是简单的'输入→LLM→输出'。6 个节点把每一步的职责切清楚，每步可独立测试。"

**追问 J1-5. 能力层（RAG/Tools/SQL安全/数据库）之间有依赖关系吗？谁依赖谁？**

**回答**："能力层依赖关系：text2sql.py 依赖 rag/retriever.py（检索知识）和 agent/prompts.py（加载模板）；sql_runner.py 依赖 security/sql_validator.py（校验）和 database/execute.py（执行）；tools/search_schema.py 依赖 rag/retriever.py；tools/execute_sql.py 依赖 agent/sql_runner.py。能力层之间不直接依赖——工具调能力层，能力层调基础设施层。"

> **代码锚点**：`app/agent/graph.py:_build_state`、`app/agent/nodes.py:set_helpers`

### K. 技术选型

**Q K1. 为什么选 FastAPI 而不是 Flask / Django？**

**回答**：
"三个硬理由：① 原生 async——LangGraph 是 async、aiomysql 是 async、SSE 流式是 async，全异步链路没有线程池转接的别扭；② Pydantic 深度集成——请求/响应模型即文档即校验；③ 自动 OpenAPI 文档（/docs）。"

**追问 K1-1. FastAPI 的原生异步对项目有什么具体好处？**

**回答**："原生异步对项目的具体好处：LangGraph 的 ainvoke 和 astream 是 async 的，aiomysql 连接池是 async 的，SSE StreamingResponse 是 async 的。如果用 Flask（同步框架），异步操作要在线程池里跑，有线程池转接的开销和别扭。FastAPI 全链路 async，没有这个问题。"

**追问 K1-2. 为什么不用 SQLAlchemy？直接写 SQL 有什么好处和坏处？**

**回答**："不用 SQLAlchemy 是因为这个 5 表纯读项目里 ORM 的核心价值（对象关系映射）不存在。直接写 SQL 和 Text-to-SQL 主题一致——项目里所有 SQL 都是显式的。好处是可讲性强、没有额外抽象层。坏处是查询复杂度上来后需要自己管理连接和 cursor，但 aiomysql 连接池已经处理了。"

**追问 K1-3. 为什么选 aiomysql 而不是 PyMySQL？异步驱动和同步驱动的区别在什么场景下重要？**

**回答**："aiomysql 是异步驱动，PyMySQL 是同步驱动。区别在这个项目很重要：FastAPI 是异步框架，用同步驱动会阻塞事件循环。aiomysql 的连接池也是异步的，和 FastAPI 的 async 链路无缝衔接。"

**Q K2. 为什么选 LangGraph 而不是 LangChain 的 LCEL 链或 AgentExecutor？**

**回答**：
"LangGraph 解决三个 LCEL 链和 AgentExecutor 解决不了的问题：条件路由、状态持久化、流式协议。"

**追问 K2-1. LCEL Chain 有什么局限？表达不了什么？**

**回答**："LCEL Chain 是单向流水线，表达不了'根据意图分流''根据检索质量绕行'这种条件路由，也表达不了状态跨步骤持久化。Chain 是线性的，图可以分支。"

**追问 K2-2. AgentExecutor 是自主循环，为什么不要自主循环？**

**回答**："AgentExecutor 是自主循环，LLM 自己决定下一步干嘛——决策权在模型手里。这不符合安全要求：SQL 只读必须由代码强制保证。LangGraph 的流程由图的边决定，LLM 只在节点内干活。"

**追问 K2-3. LangGraph 的条件边和普通 if-else 有什么区别？多了什么能力？**

**回答**："条件边本质上就是 if-else，但 LangGraph 多了三样东西：① 结构自省（/api/graph/structure 直接导出图结构给前端画图）；② 状态持久化（checkpointer 免费拿到多轮对话）；③ 流式协议（astream 按节点粒度吐进度，SSE 端点零侵入实现）。手写 if-else 这些都要自己搞。"

**追问 K2-4. 为什么不用 AutoGen / CrewAI / Dify？**

**回答**："不用 AutoGen/CrewAI 是因为它们主打多 Agent 协作，我的问题里不需要多个角色——一个受控流水线 + 一个工具决策点就够了，引入多框架是负复杂度。不用 Dify 是因为它低代码黑盒，我在做的是展示工程实现能力，而且平台的自定义安全策略受限。"

**追问 K2-5. LangGraph 的 checkpointer 给项目带来了什么免费能力？**

**回答**："checkpointer 给项目带来了三个免费能力：多轮对话上下文（读上一轮 State）、跨轮标志位管理（虽然需要手动重置）、图执行回放（/api/graph/trace）。"

**Q K3. 为什么选 Chroma 而不是 FAISS / Milvus？**

**回答**：
"看规模：几十个知识块、单机 demo，Chroma 是嵌入式（进程内、持久化到本地目录），零部署零运维，API 最简单。"

**追问 K3-1. Chroma 是嵌入式是什么意思？和不嵌入有什么区别？**

**回答**："嵌入式意思是 Chroma 运行在进程内，数据持久化到本地目录（data/chroma/），不需要单独部署服务。不嵌入（如 Milvus）是独立服务，需要单独启动和管理。"

**追问 K3-2. 如果数据量涨到百万级向量，Chroma 还够用吗？什么时候该换？**

**回答**："百万级向量 Chroma 可能不够——它的定位是轻量级嵌入式。百万级应该换 Milvus 或 Qdrant。但这个项目的向量数量是几十个知识块，Chroma 绰绰有余。换库只动 vector_store.py 一个文件。"

**追问 K3-3. 换向量库要改哪些代码？改动面大吗？**

**回答**："换向量库要改 app/rag/vector_store.py——VectorStore 类的 add() 和 query() 方法实现。检索逻辑收敛在这一个文件里，retriever.py 调的是 VectorStore 的接口，不直接操作 Chroma。改动面是一个文件。"

**追问 K3-4. FAISS 是库不是数据库，这句话怎么理解？Milvus 呢？**

**回答**："FAISS 是库不是数据库——它只做向量检索，持久化和元数据过滤要自己补。Milvus 是独立服务——为亿级向量设计，有完整的 CRUD、分片、副本。在这个规模（几十个块）用 FAISS 要自己补持久化，用 Milvus 要部署服务，都是负担。"

**Q K4. 为什么选 sqlglot 做安全校验？**

**回答**：
"sqlglot 是 SQL 解析器，能把 SQL 字符串解析成语法树（AST），让我们按结构而不是按字符串检查 SQL。选它因为它纯 Python、支持多方言、解析后可以做 AST 级别的检查和改写。"

**追问 K4-1. sqlglot 是什么？它解析 SQL 的原理是什么？**

**回答**："sqlglot 的原理：调 parse_one(sql, dialect='mysql') 返回一个 AST 根节点。AST 里每个 SQL 元素都是一个 Node 对象（Select、From、Where、Function 等）。我们可以遍历这棵树检查有没有危险节点。"

**追问 K4-2. 为什么不用正则 / 字符串匹配做校验？**

**回答**："不用正则/字符串匹配是因为至少三个洞：注释绕过（DELETE/**/FROM 字符串里有 DELETE 但语义可能不同）、大小写和空白变形、多语句切分。AST 方案里 DELETE 无论怎么变形，解析出来一定是 Delete 节点，藏不住。"

**追问 K4-3. sqlglot 有没有盲区？什么情况会误判？**

**回答**："sqlglot 的盲区：方言差异——某些 MySQL 特有语法可能解析成 Command 节点。我的处理是把 Command 也列入黑名单，宁可误杀不放过。另外它不做 schema 校验（不连库查 information_schema），所以表名/列名是否存在它不知道——这是改进项。"

**追问 K4-4. 除了 sqlglot 还有哪些 SQL 解析工具？为什么选它？**

**回答**："其他 SQL 解析工具：sqlparse（纯解析不做语义分析，能力弱于 sqlglot）、ANTLR（通用解析器框架，需要自己写语法规则，太重）。sqlglot 纯 Python、开箱即用、支持方言转换、能做 AST 改写（注入 LIMIT），最适合。"

> **代码锚点**：`app/main.py`、`app/llm/client.py`、`app/rag/vector_store.py`、`app/security/sql_validator.py`

### M. 配置与密钥管理

**Q M1. 项目的配置怎么管理的？**

**回答**：
"pydantic-settings 统一收口：所有配置是 Settings 类字段，从环境变量 + .env 读取，get_settings() 用 @lru_cache 提供单例。密钥只存在于环境变量，代码里只有占位默认值。"

**追问 M1-1. `pydantic-settings` 怎么工作的？从哪里读配置？**

**回答**："pydantic-settings 从环境变量和 .env 文件读取配置。Settings 类继承 BaseSettings，每个字段对应一个环境变量（如 llm_api_key 对应 LLM_API_KEY）。字段有类型标注和默认值。"

**追问 M1-2. `get_settings()` 用了 `@lru_cache`，为什么？不缓存会怎样？**

**回答**："@lru_cache 缓存 Settings 实例为单例。不缓存的话每次 get_settings() 都创建新实例、重新读环境变量——配置不变所以缓存合理。测试时如果要覆盖配置，可以 monkeypatch get_settings 或直接设环境变量。"

**追问 M1-3. API Key 和数据库密码怎么管的？代码里有明文吗？**

**回答**："API Key 和数据库密码只在环境变量和 .env 文件里。代码里 config.py 的字段有默认值但都是占位符（如 llm_api_key='sk-xxx'）。.env 在 .gitignore 里，仓库里只有 .env.example。"

**追问 M1-4. `.env` 和 `.env.example` 的区别？为什么仓库里只有 `.env.example`？**

**回答**：".env 是真实配置（有真实 key 和密码），.env.example 是模板（只有占位值和注释）。仓库里只有 .env.example 是为了：不泄露密钥、新人知道需要配哪些变量。"

**追问 M1-5. Docker 部署时密钥怎么注入容器的？**

**回答**："Docker 部署时 docker-compose.yml 里用 ${VAR} 语法从宿主环境注入。比如 DB_PASSWORD: ${DB_PASSWORD} 从宿主的环境变量读取，容器内通过环境变量访问。"

### N. 前端设计

**Q N1. 前端为什么用 Vue3 CDN 单文件，不用 Vite 工程？**

**回答**：
"刻意的。前端定位是'后端能力的演示窗口'，核心信息架构是事件时间线。CDN 单文件方案零构建、零 node_modules、由 FastAPI 直接托管（单进程部署），部署复杂度为零。"

**追问 N1-1. CDN 单文件方案的优缺点是什么？**

**回答**："CDN 方案优点：零构建（不需要 node_modules/webpack/vite）、单进程部署（FastAPI 直接托管）、代码集中在一个文件好审查。缺点：没有组件化（代码全在一个文件里）、没有热更新、没有 TypeScript 类型检查。"

**追问 N1-2. 如果产品要求前端要有用户登录、历史记录、多会话切换，这个前端还够用吗？怎么改？**

**回答**："如果产品要求用户登录、历史记录、多会话：CDN 单文件不够用。需要改成 Vite + Vue3 工程化：加路由（多页面）、状态管理（Pinia 多会话状态）、持久化（localStorage 存历史）、组件化（聊天窗口、时间线、结果展示拆组件）。后端 API 不需要改——SSE 端点已经支持多会话（conversation_id）。"

**追问 N1-3. 前端怎么消费 SSE 的？为什么不用 EventSource？**

**回答**："前端用 fetch 读 response.body 的 ReadableStream 消费 SSE，不用 EventSource。因为 EventSource 只支持 GET 且不能带自定义 body——我的端点是 POST（question 在请求体里）。"

**追问 N1-4. fetch 读 ReadableStream 手动解析 SSE 帧，具体怎么解析的？**

**回答**："fetch 拿到 response 后，用 response.body.getReader() 获取 ReadableStream。手动按空行（\\n\\n）切帧，每帧内按行解析 event: 和 data: 两行。逻辑封装在 streamSSE 函数里，约 20 行。"

> 目标：顺着一个点层层往下追问，模拟真实面试的连环拷问。

### O. AgentState 深挖

**Q O1. AgentState 有哪些字段？你最关注的是哪个？**

**回答**：
"AgentState 是 TypedDict，所有节点共享。关键字段：question、conversation_id、intent、retrieved_chunks、schema_needs_tool、tool_called、tool_results、generated_sql、generated_reasoning、query_result、row_count、final_answer、node_path、error、prev_question/prev_sql/prev_answer。我最关注的是 intent——它决定走哪条条件边。"

**追问 O1-1. `intent` 字段谁写的？值有哪些可能？**

**回答**："intent 由 intent_node 写入。值有两种：'DATA_QUERY'（查数据，走 SQL 流水线）和 'CHAT'（闲聊，直达 report）。"

**追问 O1-2. `retrieved_chunks` 的数据结构是什么？里面存的是什么？**

**回答**："retrieved_chunks 是 list[KnowledgeChunk]。每个 chunk 有 id、text、type（'schema' 或 'business'）、source、title。schema 类型是表结构说明，business 类型是业务规则。"

**追问 O1-3. `schema_needs_tool` 什么时候为 True？谁设的？**

**回答**："schema_needs_tool 在 schema_recall_node 里设置。当召回结果为空，或召回的 chunks 里没有 type='schema' 的块时，设为 True——没有表结构 SQL 生成必然编造，所以触发工具绕行让 LLM 换关键词再查。"

**追问 O1-4. `node_path` 是怎么追加的？每个节点都追加吗？**

**回答**："node_path 是每个节点都追加的。节点在自己的 return dict 里写 node_path: state.get('node_path', []) + ['节点名']。/api/graph/trace 返回这个路径。"

**追问 O1-5. `error` 字段在哪个节点写的？写了 error 之后图会中断吗？为什么？**

**回答**："error 字段任意节点都可以写。写了 error 后图不中断——这是设计决策：错误信息写进 state 继续走，最后 API 响应里 error 字段有信息，而不是 500 白屏。report_node 会检查 error 有没有值，有就生成兜底错误文案。"

**追问 O1-6. `prev_question` / `prev_sql` / `prev_answer` 谁写的？什么时候写的？**

**回答**："prev_question/prev_sql/prev_answer 由 build_turn_input() 在每轮入口写入。它从 checkpointer 用 aget_state 读上一轮的 question、generated_sql、final_answer。"

**追问 O1-7. `skip_execute` 和 `skip_report` 是什么？什么时候用？**

**回答**："skip_execute 和 skip_report 是控制标志。skip_execute=True 时 sql_execute_node 不执行 SQL（API 调用者只想要 SQL 不想执行）。skip_report=True 时 report_node 不调 LLM（execute=False 时跳过总结）。"

**追问 O1-8. `tool_called` 在多轮对话中会有什么问题？怎么解决的？**

**回答**："tool_called 在多轮对话中的问题：checkpointer 会把上一轮的 tool_called=True 带进本轮。条件边 _route_after_recall 判定 schema_needs_tool and not tool_called——如果 tool_called 已经是 True，工具绕行路径永远不触发。解决方案是 build_turn_input() 每轮入口显式重置 tool_called=False。"

> **代码锚点**：`app/agent/state.py`、`app/agent/run_graph.py:build_turn_input`

### P. 意图分类深挖

**Q P1. `intent_node` 是怎么做意图分类的？**

**回答**：
"两步：先关键词启发式检测——如果 question 里包含'你好''hello''hi''你是谁''谢谢'等，直接返回 CHAT。关键词没命中才调 LLM 做结构化分类。LLM 用 with_structured_output(IntentLabel) 返回 {intent: 'DATA_QUERY'|'CHAT'}。"

**追问 P1-1. 关键词启发式检测了哪些词？命中后直接返回什么？**

**回答**："关键词列表：'你好''hello''hi''你是谁''谢谢''感谢'等。命中后直接返回 intent='CHAT'，should_continue=False，不调 LLM 省一次调用。"

**追问 P1-2. 关键词没命中怎么办？调 LLM 还是直接默认？**

**回答**："关键词没命中调 LLM。用 with_structured_output(IntentLabel) 强制返回结构化的 {intent: ...}，不是自由文本。"

**追问 P1-3. LLM 分类用的什么方式？结构化输出还是自由文本？**

**回答**："LLM 分类用 with_structured_output，底层是 function calling 通道。IntentLabel 是 Pydantic 模型，只有一个 intent 字段。"

**追问 P1-4. LLM 分类失败了怎么办？默认值是什么？为什么这么选？**

**回答**："LLM 分类失败默认 intent='DATA_QUERY'。这是 fail-open 策略——宁可多查一次数据库（成本）也不拒绝用户（体验）。因为大部分问题是 DATA_QUERY，默认值命中率高。"

**追问 P1-5. 为什么不全部用 LLM 分类？关键词启发式有什么好处？**

**回答**："不全用 LLM 是因为：① 省成本——闲聊问题关键词就能识别，不需要花 token 调 LLM；② 降低延迟——少一次 API 调用少几百毫秒；③ 降可靠性风险——LLM 分类可能出错，关键词不会。"

**追问 P1-6. 如果用户问"你好，查询2026年销售额"（闲聊+查数据混合），系统怎么处理？**

**回答**："混合输入（'你好，查询2026年销售额'）：关键词命中'你好' → 直接返回 CHAT → 跳过 SQL 流水线 → report_node 用 LLM 回答。这意味着查数据的需求被忽略了。改进项是：如果 question 里同时包含闲聊词和查询意图词（如'查询''销售额'），不走关键词短路，交给 LLM 判断。"

> **代码锚点**：`app/agent/nodes.py:intent_node`、`app/agent/graph.py:_classify_intent`

### Q. RAG 检索深挖

**Q Q1. `schema_recall_node` 的检索流程详细讲一下。**

**回答**：
"调用 KnowledgeRetriever.recall(question)，内部调 Chroma 的 query() 做向量相似度检索 top-K，返回 RecallResult。然后 chunks_to_prompt_parts() 把结果按 type 分成 schema_text 和 evidence_text 两个 Prompt 槽。"

**追问 Q1-1. `KnowledgeRetriever.recall(question)` 内部怎么工作的？**

**回答**："recall(question) 做的事：① 把 question 用 embedding 模型向量化；② 调 Chroma collection 的 query(query_embeddings=[向量], n_results=top_k)；③ 返回 top-K 个 KnowledgeChunk。"

**追问 Q1-2. Chroma 的 `query()` 返回什么？怎么解析的？**

**回答**："Chroma 的 query() 返回一个字典，里面有 ids、documents、metadatas、distances。我从中提取 documents（文本内容）和 metadatas（包含 type/source/title），重新组装成 KnowledgeChunk 对象。"

**追问 Q1-3. `chunks_to_prompt_parts()` 把结果分成哪两个槽？为什么分开？**

**回答**："chunks_to_prompt_parts() 把 chunks 按 type 分组：type='schema' 的拼成 schema_text（表结构槽），type='business' 的拼成 evidence_text（业务规则槽）。分开是因为职责不同：schema 回答'能用什么表/字段'，evidence 回答'怎么算'。"

**追问 Q1-4. top-K 设了多少？为什么是这个值？K 太大太小各有什么问题？**

**回答**："top-K=4，在 config.py 里配置（RAG_TOP_K=4）。K 太小可能漏掉 JOIN 需要的第二张表；K 太大相关的和半相关的都进 Prompt，token 涨、注意力被稀释。4 在我的知识密度下大约覆盖'主表 + 关联表 + 2 条规则'。"

**追问 Q1-5. 知识库怎么切片的？按什么边界切？为什么？**

**回答**："知识库按 ## 标题切片（H2 边界）。因为知识文件本来就是'一个 H2 = 一张表/一条规则'的结构化写法，按自然边界切能保证每个 chunk 语义自完整。字符切割会把一张表的字段说明拦腰斩断。"

**追问 Q1-6. 超长的小节怎么处理？有二次切分吗？**

**回答**："超长小节有递归字符二次切分。如果 ## 下的内容超过 rag_chunk_size（400字符），用 RecursiveCharacterTextSplitter 按 overlap=60 字符切分。overlap 保证切分边界处不丢失上下文。"

**追问 Q1-7. chunk 的 `type` 字段（schema / business）有什么用？**

**回答**："chunk 的 type 字段用来分 Prompt 槽位——schema 类进 schema_info 槽，business 类进 evidence 槽。让 LLM 看到结构化的知识分类。"

**追问 Q1-8. chunk 的 `id` 怎么生成的？有什么用（去重？）？**

**回答**："chunk 的 id 是'文件路径 + 小节序号'派生的稳定值。作用是去重和幂等——ensure_indexed() 重复写入时同 id 覆盖，不会重复。重建索引也天然幂等。"

**追问 Q1-9. 索引什么时候构建？重启会重建吗？怎么触发强制重建？**

**回答**："索引在首次请求时懒构建：ensure_indexed() 检查 Chroma 里有没有数据，没有就加载知识文件切片写入。重启不重建（持久化在 data/chroma/ 目录）。强制重建用 RAG_FORCE_REBUILD=True 环境变量。"

**追问 Q1-10. `ensure_indexed()` 是幂等的吗？重复调用会怎样？**

**回答**："ensure_indexed() 是幂等的。它检查 collection 里有没有数据，有就跳过，没有才写入。重复调用不会重复写入——chunk id 是稳定的，Chroma 的 add() 同 id 覆盖。"

> **代码锚点**：`app/rag/retriever.py`、`app/rag/documents.py`、`app/rag/vector_store.py`

### R. Embedding 深挖

**Q R1. 项目的 Embedding 怎么工作的？**

**回答**：
"有 API Key 时用 DashScope 的 text-embedding-v3 模型，通过 OpenAIEmbeddings 调用。没有 API Key 时自动降级为 _HashEmbedding——用 SHA-256 哈希生成 64 维向量。"

**追问 R1-1. 有 API Key 时用什么模型？在哪配置？**

**回答**："有 Key 时用 DashScope 的 text-embedding-v3。在 .env 里配置 EMBEDDING_BASE_URL、EMBEDDING_API_KEY、EMBEDDING_MODEL。通过 langchain-openai 的 OpenAIEmbeddings 调用（OpenAI 兼容协议）。"

**追问 R1-2. 没有 API Key 时用什么兜底？`_HashEmbedding` 的原理是什么？**

**回答**："_HashEmbedding 的原理：对文本做 SHA-256 哈希，取哈希值的前 64 字节映射成 64 维向量。是确定性哈希——同一段文字永远生成同一个向量。但不是语义向量——'销售额'和'订单金额'的哈希向量完全不同，即使语义相近。"

**追问 R1-3. 哈希向量和真实向量在效果上有什么区别？**

**回答**："哈希向量 vs 真实向量：哈希向量是字面相似度（词重叠），真实向量是语义相似度。'销售额最高的商品'和'查询销量排行'在真实向量里距离近，在哈希向量里可能距离远。离线模式语义检索退化为字面匹配，但流水线结构完整可测试。"

**追问 R1-4. 为什么离线模式也保留？不直接报错让用户去申请 Key？**

**回答**："保留离线模式是因为：① 测试不需要真实 API 也能跑——99 个测试全离线通过；② 降低学习和试用门槛——新人 clone 下来就能跑；③ 证明架构设计不依赖外部服务——这是工程能力展示。直接报错让用户申请 Key 会增加试用门槛。"

**追问 R1-5. 向量维度是多少？影响检索性能吗？**

**回答**："哈希向量维度是 64。真实 embedding 维度由模型决定（text-embedding-v3 是 1024 维）。维度影响检索精度——64 维的区分度不如 1024 维。但在这个规模（几十个 chunk）影响不大。"

**追问 R1-6. 如果要换 embedding 模型，已有的向量数据怎么办？需要重建吗？**

**回答**："换 embedding 模型后已有向量数据必须重建——不同模型的向量空间不兼容。删除 data/chroma/ 目录或设 RAG_FORCE_REBUILD=True，重启后 ensure_indexed() 用新模型重新向量化所有 chunk。"

> **代码锚点**：`app/rag/vector_store.py`（含 _HashEmbedding）、`app/config.py`

### S. Tool Calling 深挖

**Q S1. `tool_call_node` 的完整逻辑讲一下。**

**回答**：
"三步：① 用 bind_tools 后的模型发起一次决策调用，拿到 AIMessage 里的 tool_calls；② 按 LLM 点名的工具执行（最多 3 次）；③ 把 search_schema 找到的知识块解析回 KnowledgeChunk 合并进 state.retrieved_chunks。"

**追问 S1-1. `bind_tools()` 做了什么？工具的"说明书"是怎么传给 LLM 的？**

**回答**："bind_tools() 做的事：把每个 @tool 函数的签名 + docstring 转成 JSON Schema，作为请求的 tools 参数发给模型。docstring 就是'工具说明书'——参数含义、返回格式、什么场景该用。所以 docstring 我写得很正式。"

**追问 S1-2. LLM 返回的是什么？`AIMessage.tool_calls` 的结构是什么？**

**回答**："LLM 返回 AIMessage，里面可能带 tool_calls 字段——一个列表，每项包含 name（工具名）和 args（参数 dict）。比如 {name: 'search_schema', args: {keyword: 'orders'}}。"

**追问 S1-3. 节点拿到 LLM 的工具选择后，怎么执行的？**

**回答**："节点拿到 tool_calls 后，按 name 查注册表找到对应的 @tool 对象，调 ainvoke 执行。执行结果作为 tool_results 写进 state。"

**追问 S1-4. 每轮最多几次工具调用？为什么是这个数？超了怎么办？**

**回答**："每轮最多 3 次工具调用，MAX_TOOL_CALLS_PER_TURN=3。超出的直接不执行。3 是防御性封顶值——限制成本和攻击面，对'查 schema + 验证一条 SQL'的合理需求够用。可配置化是改进项。"

**追问 S1-5. `MAX_TOOL_CALLS_PER_TURN` 这个常量在哪？有测试吗？**

**回答**："MAX_TOOL_CALLS_PER_TURN 在 app/agent/nodes.py 顶部定义。有专门测试 test_tool_call_node_caps_tool_calls_per_turn——构造 5 个工具调用的场景，断言只执行前 3 个。"

**追问 S1-6. 工具执行失败（如 sqlglot 拒绝）怎么处理的？**

**回答**："工具执行失败（如 sqlglot 拒绝）：工具捕获后返回 {'error': '拒绝原因'} 的 JSON——不是抛异常。因为'查询被安全策略拒绝'是工具的合法输出，LLM 需要读到拒绝原因才能调整。"

**追问 S1-7. 工具返回 JSON 而不是抛异常，这个设计有什么好处？**

**回答**："返回 JSON 的好处：① LLM 能读到错误信息（JSON 就是文本，它读得懂）；② 节点能解析 JSON 里的 error 字段判断成败；③ 不抛异常不会中断图——异常会导致图中断，JSON 返回让图继续走。"

**追问 S1-8. `_interpret_tool_output()` 怎么判断工具成功还是失败的？看什么字段？**

**回答**："_interpret_tool_output() 通过解析工具返回 JSON 里的 error 字段判断成败——有 error 字段就是失败，没有就是成功。不看有没有抛异常——'没有异常'不等于'成功'，因为工具把 sqlglot 拒绝以正常返回回传了。"

**追问 S1-9. search_schema 工具返回的 chunks 怎么 merge 到 state 里的？**

**回答**："search_schema 返回的 JSON 里有 chunks 数组，chunks_from_tool_output() 把 JSON 反序列化成 KnowledgeChunk 对象列表，合并到 state.retrieved_chunks。"

**追问 S1-10. 为什么工具结果和 RAG 结果在下游看来是"同一种东西"？**

**回答**："工具结果和 RAG 结果在下游看来是同一种东西——都是 KnowledgeChunk 对象列表，存在 state.retrieved_chunks 里。sql_generate_node 消费时不需要区分来源——不管是 RAG 召回的还是工具检索的，格式一样、Prompt 槽位一样。这是关键设计：不需要为工具结果单独开数据通道。"

> **代码锚点**：`app/agent/nodes.py:tool_call_node`、`app/tools/search_schema.py`、`app/tools/execute_sql.py`

### S2. 为什么不做 ReAct 自主循环？

**回答**：
"ReAct 循环的收益是复杂多跳任务，代价是三重失控：调用次数不可控（成本）、路径不可控（调试）、行为不可控（安全）。我的场景里单轮决策够用。"

**追问 S2-1. ReAct 是什么？它和你的设计有什么区别？**

**回答**："ReAct 是'推理-行动-观察'循环——模型执行工具后观察结果，再决定下一步，直到它认为完成。我的设计是单轮决策——LLM 在 tool_call 节点做一次工具选择，节点执行后直接进 sql_generate，不回边。"

**追问 S2-2. 自主循环的三重失控是什么？成本、路径、安全分别怎么失控？**

**回答**："三重失控：成本——循环次数不可控，每次循环都调 LLM（花钱）；路径——执行路径不确定，调试时不知道走了几步；安全——自主循环可能执行危险操作。"

**追问 S2-3. 你的场景里单轮决策够用吗？什么场景必须循环？**

**回答**："单轮决策够用因为我的场景是'检索→生成→执行'，一条线走完。模型唯一需要的决策是'检索不到时用什么关键词再查'——一轮足够。多跳推理（如'先查用户再查他的订单再查订单详情'）需要循环，但我的知识库里有 JOIN 模板，LLM 一步就能生成多表 JOIN。"

**追问 S2-4. 如果要加循环，怎么加才安全？最大迭代次数放哪？**

**回答**："如果要加循环，安全加法是：状态机式循环（tool_call 可回边到自身，但设最大迭代次数计数器进 state）+ 每轮工具白名单收紧 + 超时熔断。把'循环'变成图上的受控回边，而不是跳出图的黑盒。"

**追问 S2-5. 你的条件边里有防环保护吗？具体怎么防的？**

**回答**："条件边有防环保护：_route_after_recall 判定 schema_needs_tool and not tool_called。not tool_called 保证工具路径每轮最多触发一次——即使将来有人把 tool_call 的出边改回 schema_recall，这个标志位也保证不循环。另外 build_turn_input() 每轮入口重置 tool_called=False。"

### T. SQL 生成深挖

**Q T1. `Text2SqlGenerator.agenerate()` 的完整流程讲一下。**

**回答**：
"组装 Prompt（方言+表结构+业务规则+问题+上一轮问答+硬约束）→ with_structured_output(SqlGeneration) 强制结构化 → LLM 返回 {sql, reasoning}。如果传入 chunks（来自工具调用）直接用，否则调 retriever.recall() 召回。"

**追问 T1-1. Prompt 模板有几个槽位？分别是什么？**

**回答**："Prompt 模板有 7 个槽位：dialect（MySQL 8.0）、schema_info（表结构）、evidence（业务规则）、question（用户问题）、previous_step_results（上一轮问答）、execution_description（执行描述）、max_rows（行数上限）。"

**追问 T1-2. `schema_info` 槽的内容从哪来的？RAG 召回还是全量文档？**

**回答**："schema_info 槽来自 RAG 召回的 type='schema' 的 chunks。如果 RAG 召回 0 条，走全量兜底——business_knowledge.py 的 schema_doc() 读取 data/knowledge/schema/ecommerce.md 全量注入。"

**追问 T1-3. `evidence` 槽放什么？和 `schema_info` 有什么区别？**

**回答**："evidence 槽放 type='business' 的 chunks——业务规则。和 schema_info 的区别：schema 回答'能用什么表/字段'，evidence 回答'怎么算'（如'销售额=paid订单金额之和'）。同一问题口径不同 SQL 完全不同。"

**追问 T1-4. `previous_step_results` 槽什么时候有内容？多轮对话怎么注入的？**

**回答**："previous_step_results 槽在多轮对话时有内容。build_turn_input() 从 checkpointer 读上一轮的 question/SQL/answer 注入 state 的 prev_* 字段。sql_generate_node 把它们格式化进 Prompt。"

**追问 T1-5. `with_structured_output(SqlGeneration)` 做了什么？底层怎么实现的？**

**回答**："with_structured_output(SqlGeneration) 把 Pydantic 模型转成 JSON Schema，走 function calling 通道让模型按 schema 生成。拿到的直接是类型正确的对象，保证 sql 字段没有 markdown 围栏、没有解释文字。"

**追问 T1-6. 如果模型不支持 function calling 怎么办？降级到什么？**

**回答**："模型不支持 function calling 时 LangChain 降级为 JSON mode 或 prompt 约定。即使降级，最后还有 sqlglot 解析兜底——解析失败的 SQL 根本到不了数据库。"

**追问 T1-7. `SqlGeneration` 有哪些字段？`reasoning` 字段有什么用？**

**回答**："SqlGeneration 有两个字段：sql（生成的 SQL 字符串）和 reasoning（LLM 的推理说明）。reasoning 有两个用：① 调试——生成错了能看到 LLM 的思路；② 传给 API 响应——用户能看到'为什么这么写'。"

**追问 T1-8. 如果 RAG 召回了 0 条 schema 知识，SQL 生成会走什么兜底？**

**回答**："RAG 召回 0 条 schema 知识的兜底：text2sql.py 的 agenerate() 里检查——如果 chunks 为空或没有 schema 类型的 chunk，调用 business_knowledge.py 的 schema_doc() 读取全量 schema 文档注入。保证 schema 槽永远不为空。"

**追问 T1-9. 如果传入的 chunks（来自工具调用）和 RAG 召回的 chunks 格式一样吗？怎么保证一致？**

**回答**："工具传来的 chunks 和 RAG 召回的 chunks 格式完全一样——都是 KnowledgeChunk 对象。agenerate() 如果传入 chunks 参数就直接用，跳过内部 recall。所以工具结果和 RAG 结果在 SQL 生成看来完全同构。"

**追问 T1-10. temperature 设了多少？为什么？对 SQL 生成有什么影响？**

**回答**："temperature=0.1，在 llm/client.py 的 get_chat_model() 里配置。低温因为 SQL 是确定性任务——同样的输入希望同样的输出，creativity 是负资产。0.1 留一点灵活性避免完全死板。"

> **代码锚点**：`app/agent/text2sql.py:agenerate`、`app/prompts/new_sql_generate.txt`、`app/llm/client.py`

### U. SQL 安全校验深挖

**Q U1. `validate_and_rewrite()` 的四道检查分别是什么？**

**回答**：
"四道：① 空 SQL 检查；② 多语句检查（分号分隔）；③ sqlglot AST 解析——顶层白名单只认 SELECT，全树黑名单禁止写操作节点；④ 危险函数黑名单 + 自动补 LIMIT 1000。"

**追问 U1-1. 第一道：空 SQL 怎么检查？为什么要查？**

**回答**："空 SQL 检查：if not sql or not sql.strip(): raise SqlValidationError。因为空 SQL 执行没意义且可能暴露连接池行为。"

**追问 U1-2. 第二道：多语句怎么检查的？`;` 分隔的多语句为什么危险？**

**回答**："多语句检查：检查 SQL 里有没有分号。分号分隔的多语句（SELECT 1; DROP TABLE users）危险因为第二条语句可能执行写操作。sqlglot 的 parse_one 只解析第一条，后面的会被忽略——但我在解析前就拒绝了。"

**追问 U1-3. 第三道：顶层白名单只允许什么？WITH...SELECT 算不算？**

**回答**："顶层白名单只允许 exp.Select。WITH...SELECT 也算——sqlglot 解析 WITH...SELECT 时根节点是 Select（WITH 是 Select 的一个属性），所以通过。INSERT/UPDATE/DELETE/DROP 的根节点分别是 Insert/Update/Delete/Drop，不在白名单里被拒。"

**追问 U1-4. 第四道：全树黑名单检查了哪些节点类型？为什么要在全树检查而不只是顶层？**

**回答**："全树黑名单检查遍历整个 AST，禁止的节点类型：Insert、Update、Delete、Merge、Create、Drop、Alter、TruncateTable、Grant、Revoke、Command、Block。全树检查而不只是顶层是因为子查询里可能藏写操作——SELECT * FROM (DELETE FROM users) AS t——虽然这种语法 MySQL 不支持，但 AST 层面能检测到。"

**追问 U1-5. 子查询里藏 `DELETE` 能被抓到吗？怎么抓的？**

**回答**："子查询里藏 DELETE 能被抓到。AST 遍历时会走到子查询的节点，发现 Delete 类型节点在黑名单里，直接拒绝。"

**追问 U1-6. 危险函数黑名单有哪些？SLEEP / BENCHMARK / LOAD_FILE 分别有什么危害？**

**回答**："危险函数黑名单：SLEEP（让查询卡住消耗资源）、BENCHMARK（重复执行表达式消耗 CPU）、LOAD_FILE（读取服务器文件系统）。这三个是 MySQL 里可能被滥用的信息泄露/资源消耗函数。"

**追问 U1-7. LIMIT 1000 是怎么注入的？是改原始 SQL 还是改 AST 后重新生成？**

**回答**："LIMIT 1000 是在 AST 上注入的。检查 AST 里有没有 limit 节点，没有就创建一个 Limit 节点设值为 1000 挂到 Select 上，然后 sql() 方法重新生成 SQL 字符串。所以执行的是改写后的 SQL 不是原始 SQL。"

**追问 U1-8. 如果 SQL 已经有 LIMIT 500，校验器会覆盖吗？为什么尊重用户的 LIMIT？**

**回答**："SQL 已经有 LIMIT 500 时不覆盖——尊重用户的 LIMIT。因为用户显式写了 LIMIT 说明知道想要多少行。但也不强加硬上限（如 LIMIT 不能超过 10000）——这是已知取舍，改进项是加硬上限防恶意大查询。"

**追问 U1-9. 如果用户写 `LIMIT 999999999` 呢？有硬上限吗？这是不是个隐患？**

**回答**："LIMIT 999999999 目前不会被拦。这是已知隐患——改进项是加硬上限（如 max_rows=10000），AST 里 LIMIT 值超过上限就改写为上限。现在 default_max_rows=1000 只在不写 LIMIT 时注入，已有 LIMIT 不检查值。"

**追问 U1-10. `ALLOWED_ROOT_TYPES` 和 `FORBIDDEN_NODE_TYPES` 的关系是什么？白名单+黑名单双重检查有必要吗？**

**回答**："ALLOWED_ROOT_TYPES 是白名单（只允许 Select），FORBIDDEN_NODE_TYPES 是黑名单（全树禁止写操作）。双重检查有必要：白名单保证顶层只能是 SELECT，黑名单保证子查询里也藏不住写操作。白名单管'顶层'，黑名单管'全树'，互补。"

**追问 U1-11. sqlglot 解析失败（语法不合法的 SQL）会怎样？是抛异常还是返回错误？**

**回答**："sqlglot 解析失败（语法不合法的 SQL）会抛 ParseError，我在 validate_and_rewrite 里 catch 后转成 SqlValidationError。解析不了的 SQL 更不能执行——这是'fail closed'原则。"

**追问 U1-12. 方言问题：MySQL 特有语法 sqlglot 能解析吗？解析不了怎么办？**

**回答**："MySQL 特有语法 sqlglot 基本能解析（sqlglot 支持多方言，parse_one 时指定 dialect='mysql'）。但某些极端语法可能解析成 Command 节点——我把 Command 列入黑名单，宁可误杀不放过。遇到误杀可以调整知识库的 JOIN 模板引导 LLM 生成标准语法。"

> **代码锚点**：`app/security/sql_validator.py`、`app/agent/sql_runner.py:run_select`

### V. SSE 流式推送深挖

**Q V1. SSE 端点 `stream.py` 的实现详细讲一下。**

**回答**：
"核心是 LangGraph 的 astream(stream_mode='updates')：每个节点执行完吐一次 {节点名: state增量}，映射成 SSE 事件。节点代码零改造——流式是图引擎的运行模式。"

**追问 V1-1. `astream(stream_mode="updates")` 返回什么？每次 yield 的数据结构是什么？**

**回答**："astream(stream_mode='updates') 返回一个 async generator，每次 yield 的是一个 dict：{节点名: 该节点返回的 partial state}。比如 {'intent': {'intent': 'DATA_QUERY', 'should_continue': True}}。"

**追问 V1-2. 节点名怎么映射成 SSE 事件名的？映射表在哪？**

**回答**："节点名映射成 SSE 事件名：intent→thinking、schema_recall→retrieval、tool_call→tool、sql_generate→sql、sql_execute→result、report→answer。映射逻辑在 stream.py 里用一个条件判断链。"

**追问 V1-3. 节点代码需要为流式做任何改造吗？为什么不需要？**

**回答**："节点代码不需要改造。流式是图引擎的运行模式——astream 是 LangGraph 在编译后的图上提供的流式接口，节点只管返回 dict，图引擎负责在节点完成后 yield。"

**追问 V1-4. SSE 帧的格式是什么？`event:` 和 `data:` 行怎么拼接的？**

**回答**："SSE 帧格式：event: 事件名\\ndata: JSON字符串\\n\\n。拼接是 yield f'event: {event_type}\\ndata: {json.dumps(data)}\\n\\n'。空行（\\n\\n）分隔帧。"

**追问 V1-5. `data` 为什么要 JSON 编码？不编码会怎样？**

**回答**："data 用 JSON 编码因为中文、引号、换行在裸 SSE 文本里会破坏帧结构。JSON 编码后这些字符被转义，帧结构安全。"

**追问 V1-6. 错误路径怎么处理的？setup 失败发什么事件？**

**回答**："错误路径：setup 失败（如 build_turn_input 异常）发 error 事件，data 是错误信息。流永远以 done 收尾——前端不会吊死。"

**追问 V1-7. 流的结尾发什么？前端怎么知道流结束了？**

**回答**："流结尾发 done 事件，data 是 [DONE]。前端收到 done 后关闭 fetch 流，停止读取。"

**追问 V1-8. 如果某个节点执行很慢（比如 LLM 超时 30 秒），SSE 会怎样？前端会超时吗？**

**回答**："节点执行慢（LLM 超时 30 秒）：该节点的 SSE 事件要等节点执行完才推。前端在等待期间显示上一个事件的状态（如'正在生成SQL...'）。ChatOpenAI 设了 timeout=30，30 秒后超时抛异常，节点 catch 后写 error，推送 error 事件。前端不会无限等待。"

> **代码锚点**：`app/api/stream.py`、`app/llm/client.py`（timeout=30）

### W. Checkpointer 深挖

**Q W1. checkpointer 在项目里用在哪几个地方？**

**回答**：
"三个地方：多轮上下文（build_turn_input 读上一轮 State）、跨轮标志位重置、/api/graph/trace 回放节点路径。"

**追问 W1-1. `MemorySaver` 是什么？它是内存实现还是持久化？**

**回答**："MemorySaver 是 LangGraph 的内存 checkpointer 实现——存在进程内存里，不是持久化。重启即丢。"

**追问 W1-2. thread_id 用的什么值？为什么用 conversation_id？**

**回答**："thread_id 用的 conversation_id。因为一个 conversation 就是一个会话线程，checkpointer 按 thread_id 存取 State 快照。"

**追问 W1-3. 每轮结束后 checkpointer 存了什么？完整 State 快照？**

**回答**："每轮结束后 checkpointer 存的是完整 State 快照——所有字段当前值的深拷贝。所以 aget_state 能读出上一轮的所有字段。"

**追问 W1-4. `aget_state` 和 `aget` 有什么区别？分别在哪用？**

**回答**："aget_state 是读 checkpointer 里的状态（历史快照），aget 是图执行时的实时状态。我在 build_turn_input 里用 aget_state 读上一轮历史，在 ainvoke 执行时 LangGraph 内部用 checkpointer 存当前轮。"

**追问 W1-5. 多轮对话的 `build_turn_input()` 从 checkpointer 读什么？读几轮的？**

**回答**："build_turn_input 从 checkpointer 读上一轮的 question、generated_sql、final_answer 三个字段。只读一轮——读到的是上一轮结束时的完整快照，从中提取这三个字段。"

**追问 W1-6. checkpointer 会不会把上一轮的 `tool_called=True` 带进本轮？怎么处理的？**

**回答**："checkpointer 会把上一轮的 tool_called=True 带进本轮——因为存的是完整快照。build_turn_input 里显式重置 tool_called=False、schema_needs_tool=False、tool_results=[]、tool_error=''。不重置的话条件边判定 not tool_called 永远 False，工具路径永远不触发。"

**追问 W1-7. `get_compiled_graph()` 用了 `@lru_cache`，图只编译一次。如果 checkpointer 要换实现怎么办？**

**回答**："get_compiled_graph 用 @lru_cache 缓存编译后的图。换 checkpointer 实现需要清缓存——但 @lru_cache 没有 clear 方法（在 functools.lru_cache 对象上有 .cache_clear()）。实际操作是换实现后重启服务。或者改 get_compiled_graph 不缓存，每次编译——编译开销不大。"

**追问 W1-8. 重启服务后内存里的 checkpointer 数据全丢了，用户的多轮对话就断了，怎么解决？**

**回答**："重启后 MemorySaver 数据全丢。解决：换持久化 checkpointer（LangGraph 提供 SqliteSaver/PostgresSaver）。换实现只改 get_compiled_graph 里 MemorySaver() 那一行——这就是'为规模化预留正确结构'。"

> **代码锚点**：`app/agent/graph.py:get_compiled_graph`、`app/agent/run_graph.py:build_turn_input`

### X. 数据库连接池深挖

**Q X1. MySQL 连接池怎么管理的？**

**回答**：
"模块级 _pool 全局单例。init_pool() 在 FastAPI lifespan 启动时调用创建连接池，close_pool() 在关闭时调用。execute() 和 execute_scalar() 从池里获取连接执行。"

**追问 X1-1. `init_pool()` 在什么时候调用的？FastAPI lifespan 是什么？**

**回答**："init_pool() 在 main.py 的 lifespan 钩子里调用。lifespan 是 FastAPI 的生命周期管理——启动时执行 yield 之前的代码，关闭时执行 yield 之后的代码。init_pool 在 yield 前，close_pool 在 yield 后。"

**追问 X1-2. 连接池初始化失败了会怎样？服务能启动吗？为什么这么设计？**

**回答**："连接池初始化失败只记录 warning，不阻止服务启动。因为 /health 端点不需要 MySQL——即使数据库挂了，/health 也能返回 ok，让容器探针不会误杀。sql_execute_node 执行时才会发现连接池不可用。"

**追问 X1-3. `autocommit=True` 为什么这么设？只读场景有什么好处？**

**回答**："autocommit=True 因为只读场景不需要事务——SELECT 不修改数据，不需要 commit/rollback。autocommit 省掉了事务管理的开销。"

**追问 X1-4. 连接池的 `minsize` 和 `maxsize` 在哪配置？默认多少？**

**回答**："minsize 和 maxsize 在 config.py 里配置（DB_POOL_MIN 和 DB_POOL_MAX）。默认 min=1 max=10。10 个连接对于单实例 demo 够用。"

**追问 X1-5. `close_pool()` 是幂等的吗？多次调用会怎样？**

**回答**："close_pool() 是幂等的——如果 _pool 是 None（已经关闭或未初始化），直接返回不操作。多次调用安全。"

**追问 X1-6. `execute()` 和 `execute_scalar()` 的区别？分别什么时候用？**

**回答**："execute(sql, params) 返回 (rowcount, list[dict])——行数和结果列表。execute_scalar(sql, params) 返回首行首列的单个值。execute_scalar 用于 COUNT(*)、SUM() 等只需要一个值的聚合查询。"

**追问 X1-7. `DictCursor` 返回的数据结构是什么？为什么用 DictCursor 而不是普通 Cursor？**

**回答**："DictCursor 返回每行是一个 dict（{列名: 值}），而不是普通 tuple。用 DictCursor 因为：① 结果可以直接序列化成 JSON 返回 API；② LLM 总结时看到的是有列名的数据，更容易理解；③ 代码可读性更好。"

> **代码锚点**：`app/database/engine.py`、`app/database/execute.py`、`app/main.py:lifespan`

### Y. 开发中的难点

**Q Y1. 开发这个项目过程中遇到的最难的问题是什么？**

**回答**：
"一个隐蔽的跨轮状态残留 bug：上线工具路径后发现同一会话第二轮永远不再进 tool_call。"

**追问 Y1-1. 你是怎么发现的？现象是什么？**

**回答**："现象：同一会话第一轮走了 tool_call 路径，第二轮即使检索为空也不再进 tool_call——直接走 sql_generate 导致 SQL 质量下降。是手动测试多轮对话时发现的。"

**追问 Y1-2. 你的排查思路是什么？从哪开始查的？**

**回答**："排查思路：先怀疑条件边写错——但单测图路由没问题；再跑图级测试发现第二轮 state 里 tool_called 竟然是 True——根因是 checkpointer 会把上一轮的 State 带进本轮。"

**追问 Y1-3. 最终根因是什么？怎么修复的？**

**回答**："根因：checkpointer 按 thread_id 存每轮完整 State 快照。aget_state 读出来的 state 包含上一轮的所有字段值——包括 tool_called=True。而我在节点里写标志位、没在轮首清空。修复：build_turn_input() 每轮入口显式重置。"

**追问 Y1-4. 修复后怎么防止回归？有写测试吗？**

**回答**："写了专门测试 test_build_turn_input_resets_tool_flags 防止回归。还有端到端测试：同一会话发两轮请求，第二轮检索为空时断言走了 tool_call 路径。"

**追问 Y1-5. 这个 bug 让你对什么技术/概念的理解加深了？**

**回答**："这个 bug 让我对 LangGraph checkpointer 的理解从'会用'到了'知道它改变了状态的生命周期'——有持久化就有脏状态风险，轮首重置是必须的。"

> **代码锚点**：`app/agent/run_graph.py:build_turn_input`（标志位重置）

### Z. 跨轮状态残留 Bug（重点追问）

**Q Z1. 你提到 checkpointer 会把上一轮状态带进下一轮，具体说说这个问题。**

**回答**：
"上线工具路径后，同一会话第二轮永远不再进 tool_call——条件边判定 not tool_called 永远 False。"

**追问 Z1-1. 现象是什么？第二轮什么行为不正常？**

**回答**："现象：第一轮走了 tool_call（因为检索为空），第二轮即使检索还是空也不走 tool_call——直接走 sql_generate，LLM 编造表名。"

**追问 Z1-2. 你怎么定位到是 checkpointer 的问题？排查过程？**

**回答**："定位过程：先怀疑条件边写错——单测 _route_after_recall 没问题；再跑图级测试，打印第二轮入口的 state，发现 tool_called=True——是 checkpointer 带过来的。"

**追问 Z1-3. 为什么 checkpointer 会把 tool_called=True 带过来？这是 LangGraph 的设计还是 bug？**

**回答**："checkpointer 把 tool_called=True 带过来是 LangGraph 的设计——它存每轮完整 State 快照，aget_state 读出来的包含上一轮所有字段。这不是 LangGraph 的 bug，是我的 bug：我在节点里写 tool_called=True 但没在轮首清空。"

**追问 Z1-4. 你的修复方案是什么？在哪个函数里重置的？**

**回答**："修复在 build_turn_input() 里——每轮入口显式设 tool_called=False、schema_needs_tool=False、tool_results=[]、tool_error=''。"

**追问 Z1-5. 重置了哪些标志位？为什么是这几个？**

**回答**："重置了 4 个标志位：tool_called、schema_needs_tool、tool_results、tool_error。因为这 4 个是工具路径专用的，每轮应该是干净状态。其他字段如 retrieved_chunks 会被本轮覆盖不需要重置。"

**追问 Z1-6. 如果将来加了新的标志位，会不会又出现类似问题？怎么预防？**

**回答**："预防：建立'有持久化就有脏状态风险'的意识——任何新增的跨轮标志位都要在 build_turn_input 里重置。代码里加了注释提醒。也可以考虑用 dataclass 的 default_factory 自动重置，但 TypedDict 不支持。"

**追问 Z1-7. 你怎么测试验证修复有效的？测试用例怎么写的？**

**回答**："测试：test_build_turn_input_resets_tool_flags——构造一个带 tool_called=True 的 state，调 build_turn_input，断言返回的 state 里 tool_called=False。还有端到端测试：同一会话发两轮请求，第二轮检索为空时断言走了 tool_call 路径。"

> **代码锚点**：`app/agent/run_graph.py:build_turn_input`、`tests/test_multi_turn.py`

### AA. 工具执行失败排查

**Q AA1. 如果 LLM 被诱导调 `execute_sql("DROP TABLE users")`，会发生什么？**

**回答**：
"sqlglot 在 execute_sql 工具内部第一步 validate_and_rewrite() 就拦截了——在建立数据库连接之前。拦截后返回 JSON {error: 'Only SELECT is allowed...'}，不抛异常。LLM 能读到拒绝原因但没有修正机制。"

**追问 AA1-1. sqlglot 在哪一步拦截的？在建立数据库连接之前还是之后？**

**回答**："sqlglot 在 execute_sql 工具内部、run_select() 的第一步拦截。validate_and_rewrite() 解析出 Drop 节点，在 FORBIDDEN_NODE_TYPES 黑名单里，直接 raise SqlValidationError。这发生在 database/execute.py 的 execute() 之前——没有建立数据库连接。"

**追问 AA1-2. 拦截后返回什么？是抛异常还是返回 JSON？**

**回答**："拦截后 execute_sql 工具 catch 异常，返回 JSON {error: 'Only SELECT is allowed at the top level; got Drop', row_count: null, rows: []}。不是向上抛异常。"

**追问 AA1-3. LLM 能看到拒绝原因吗？它有机会修正 SQL 吗？**

**回答**："LLM 能看到拒绝原因——JSON 里的 error 字段就是文本，LLM 读得懂。但当前没有修正机制——工具结果写进 state 后图继续走 sql_generate，LLM 会基于已有的知识重新生成 SQL。改进项是加'读到工具失败后修正 SQL'的回边。"

**追问 AA1-4. 如果 sqlglot 本身有 bug 没拦住怎么办？还有兜底吗？**

**回答**："如果 sqlglot 本身有 bug 没拦住，第 4 层防线兜底——MySQL readonly 账号物理上没有 DROP 权限。即使 SQL 到了数据库也会被 MySQL 拒绝（ERROR 1227: Access denied）。双重保险。"

**追问 AA1-5. 你有针对这个场景的测试吗？测试怎么写的？测试名叫什么？**

**回答**："有专门测试：test_tool_call_node_malicious_execute_sql_is_blocked——模拟 LLM 调 execute_sql('DELETE FROM orders')，断言返回的 tool_results 里 ok=False、错误信息含拒绝原因、tool_error 被设置、且图没有崩。全部离线——因为校验在建立连接之前，不需要 MySQL 在跑。"

> **代码锚点**：`app/tools/execute_sql.py`、`tests/test_tools.py`

### AB. LLM 调用超时/失败排查

**Q AB1. 如果 LLM API 超时了，系统什么表现？**

**回答**：
"设计目标是'永不白屏，逐级降级'。每个节点 catch 异常后写 error 字段继续走，SSE 流永远以 done 收尾。"

**追问 AB1-1. ChatOpenAI 的 timeout 设了多少？在哪配置？**

**回答**："ChatOpenAI 的 timeout=30 秒，在 llm/client.py 的 get_chat_model() 里配置。30 秒后抛 httpx.TimeoutException。"

**追问 AB1-2. 超时后 intent_node 会怎样？默认值是什么？为什么这么选？**

**回答**："intent_node 超时：catch 异常后默认 intent='DATA_QUERY'，should_continue=True。这是 fail-open——宁可多查不可不响应。"

**追问 AB1-3. 超时后 sql_generate_node 会怎样？SQL 为空时怎么处理？**

**回答**："sql_generate_node 超时：catch 异常后 generated_sql=''、generated_reasoning='LLM 生成失败'。sql_execute_node 检查 SQL 为空时跳过执行，写 error。"

**追问 AB1-4. 超时后 report_node 会怎样？有兜底文案吗？**

**回答**："report_node 超时：catch 后用兜底文案——直接展示 SQL 执行结果（原始行数据），不做自然语言总结。用户至少能看到数据。"

**追问 AB1-5. SSE 流在 LLM 超时时会怎样？前端会看到什么？**

**回答**："SSE 流在 LLM 超时时：节点 catch 异常后写 error，图继续走到下一个节点。SSE 会推 error 事件（data 是错误信息），最后推 done。前端显示错误信息但不吊死。"

**追问 AB1-6. 用户看到的是什么？白屏还是错误信息？为什么不会白屏？**

**回答**："用户看到的是错误信息或兜底数据，不是白屏。因为每个节点都有 try-catch，异常被吸收在节点内。API 响应永远返回结构化数据（有 error 字段），SSE 永远以 done 收尾。"

> **代码锚点**：`app/llm/client.py`（timeout=30）、`app/agent/nodes.py` 各节点的 try-catch

### AC. RAG 检索质量排查

**Q AC1. 如果用户问的问题 RAG 召回不到相关知识怎么办？**

**回答**：
"三级兜底：RAG 召回为空 → 条件边绕行 tool_call（LLM 换关键词调 search_schema）→ tool_call 也查不到 → sql_generate 用全量知识文档兜底。"

**追问 AC1-1. 召回为空时 `schema_recall_node` 做了什么？**

**回答**："召回为空时 schema_recall_node 检查：如果 retrieved_chunks 为空或没有 type='schema' 的 chunk，设 schema_needs_tool=True。"

**追问 AC1-2. `schema_needs_tool` 什么时候设为 True？判定标准是什么？**

**回答**："schema_needs_tool=True 的判定标准：召回结果为空，或者召回的 chunks 里没有任何 type='schema' 的块——没有表结构 SQL 生成必然编造。用规则判定而不是置信度模型，因为这是'必然失败'的充分条件。"

**追问 AC1-3. 走了 tool_call 之后还检索不到怎么办？**

**回答**："走了 tool_call 还检索不到：search_schema 工具也返回空。tool_call_node 把空结果写进 state，但 schema_needs_tool 设为 False（防循环），图继续走 sql_generate。"

**追问 AC1-4. tool_call 也查不到，sql_generate 有最后兜底吗？**

**回答**："tool_call 也查不到时 sql_generate 有最后兜底：agenerate() 里检查如果 chunks 为空或没有 schema 类 chunk，调用 business_knowledge.py 的 schema_doc() 读取全量 schema 文档注入。"

**追问 AC1-5. 三级兜底（RAG → 工具 → 全量文档）之后 schema 槽还会为空吗？**

**回答**："三级兜底后 schema 槽不会为空。RAG → 工具 → 全量文档。全量文档是 data/knowledge/schema/ecommerce.md 的完整内容，包含所有 5 张表的 DDL 摘要和 JOIN 模板。"

**追问 AC1-6. 如果 schema 槽为空，LLM 会怎样？编造表名的概率有多大？**

**回答**："如果 schema 槽为空（三级兜底全失败——比如知识文件被删了），LLM 会编造表名。概率取决于 LLM 模型——但 sqlglot 会拦截不合法的 SQL，readonly 账号会拒绝不存在的表查询。最坏情况是查询失败返回错误，不会造成安全问题。"

**追问 AC1-7. 怎么评估"召回质量差"？有量化指标吗？**

**回答**："评估召回质量：检索层准备'(问题, 应召回的 chunk id)'标注对算 recall@K。项目里有内容守卫测试（test_knowledge_content.py 保证知识库包含 5 张表和销售额/退款规则），但标注对是改进项。端到端层准备标注题目集看最终 SQL 正确率。"

> **代码锚点**：`app/agent/nodes.py:schema_recall_node`、`app/agent/text2sql.py:agenerate`、`tests/test_knowledge_content.py`

### AD. 线上故障场景

**Q AD1. 如果线上 MySQL 突然挂了，系统什么表现？**

**回答**：
"sql_execute_node 会失败，错误写进 state['error']，图不中断继续走到 report。report 用兜底文案。用户看到错误信息，SSE 流正常结束。"

**追问 AD1-1. 哪个节点会失败？`sql_execute_node`？**

**回答**："sql_execute_node 失败——execute() 调 get_pool() 时连接池可能已创建但连接失败抛异常。节点 catch 后写 error。"

**追问 AD1-2. 连接池 `get_pool()` 返回什么？抛异常吗？**

**回答**："get_pool() 如果连接池未初始化抛 RuntimeError；如果已初始化但 MySQL 挂了，aiomysql 获取连接时抛 OperationalError。"

**追问 AD1-3. 错误信息会写进 `state["error"]` 吗？图会中断吗？**

**回答**："错误信息写进 state['error']。图不中断——节点 return {'error': '...'} 继续。report_node 检查 error 有值就生成错误兜底文案。"

**追问 AD1-4. 用户看到什么？SSE 流正常结束吗？**

**回答**："用户看到：SSE 推到 result 事件时 data 可能是错误信息，answer 事件是兜底文案如'查询执行失败，请稍后重试'。流以 done 收尾。"

**追问 AD1-5. `/health` 端点能检测到 MySQL 挂了吗？为什么能/不能？**

**回答**："/health 端点不能检测到 MySQL 挂了——因为它只检查 FastAPI 应用存活，不检查 MySQL 连通性。改进项是加 /health/ready 端点检查 MySQL 连通性，用于 readiness 探针。"

**追问 AD1-6. MySQL 恢复后需要重启服务吗？连接池能自动重连吗？**

**回答**："MySQL 恢复后不需要重启服务——aiomysql 连接池会自动重连。但需要 init_pool 时的连接池配置正确。如果连接池在 MySQL 挂掉期间被关闭了（close_pool），需要重启服务重新 init_pool。"

> **代码锚点**：`app/database/engine.py`、`app/agent/nodes.py:sql_execute_node`、`app/main.py:lifespan`

## 六、性能、并发、优化相关问题

### AE. 延迟分析

**Q AE1. 一次完整的 DATA_QUERY 请求，涉及几次 LLM 调用？分别在哪个节点？**

**回答**：
"正常路径（不走工具）：3 次——意图分类、SQL 生成、报告总结。如果走了 tool_call 多一次工具决策调用。"

**追问 AE1-1. 意图分类算一次 LLM 调用吗？**

**回答**："意图分类算一次 LLM 调用——但如果关键词命中（'你好''谢谢'）就不调 LLM。所以闲聊是 0 次 LLM（直达 report 后是 1 次总结）。"

**追问 AE1-2. 如果走了 tool_call，又是几次 LLM 调用？**

**回答**："走了 tool_call 多一次：tool_call_node 里 bind_tools 后的决策调用是 1 次 LLM。所以走工具路径是 4 次。"

**追问 AE1-3. SQL 生成一次、报告总结一次，总共最多几次？**

**回答**："总计最多 4 次：意图分类 1 + 工具决策 1 + SQL 生成 1 + 报告总结 1。不走工具是 3 次。"

**追问 AE1-4. 这些 LLM 调用是串行的还是并行的？能优化成并行吗？**

**回答**："这些 LLM 调用是串行的——每个节点等前一个节点完成才开始。不能并行因为后面的节点依赖前面的输出（SQL 生成依赖检索结果，执行依赖 SQL）。"

**追问 AE1-5. 用户体验到的端到端延迟大概多少？瓶颈在哪？**

**回答**："端到端延迟约 3-8 秒（取决于 LLM 响应速度）。瓶颈在 LLM 调用——每次约 1-2 秒，3 次串行就是 3-6 秒。MySQL 查询通常 <100ms，Chroma 检索 <50ms。"

**追问 AE1-6. 如果要优化延迟，你会先优化哪个环节？怎么优化？**

**回答**："优化优先级：① 意图分类用关键词短路更多场景（省 1 次调用）；② report 节点可以流式输出（astream 让用户边看边等）；③ SQL 生成和报告可以用更快的模型（如 deepseek-coder 专门做 SQL）。"

### AF. 并发场景

**Q AF1. 如果 100 个用户同时问问题，系统扛得住吗？**

**回答**：
"链路是全异步的，单实例能扛一定并发，但瓶颈在 LLM API 的 RPM 限制和 MySQL 连接池。"

**追问 AF1-1. 链路是全异步的，单实例能扛多少并发？瓶颈在哪？**

**回答**："单实例并发瓶颈在两处：LLM API 的 RPM（requests per minute）配额和 MySQL 连接池 maxsize=10。FastAPI 本身的异步框架可以处理上千并发连接，但下游资源有限。"

**追问 AF1-2. LLM API 的 RPM 限制是什么？100 个用户同时请求会触发限流吗？**

**回答**："LLM API 的 RPM：DashScope/DeepSeek 都有 RPM 限制（如 60 RPM）。100 个用户同时请求会触发 429 限流。需要做请求排队和配额管理。"

**追问 AF1-3. MySQL 连接池 maxsize=10，100 个并发查询会怎样？连接不够时排队还是报错？**

**回答**："MySQL 连接池 maxsize=10：100 个并发查询时，前 10 个拿到连接执行，后 90 个排队等待。aiomysql 的 pool 会 await 等待连接释放，不会报错但会超时。可以增大 maxsize 或加查询超时。"

**追问 AF1-4. Chroma 向量检索是线程安全的吗？多线程同时 query 会怎样？**

**回答**："Chroma 是嵌入式（进程内），多线程同时 query 是线程安全的——Chroma 内部有锁。但高并发下可能成为瓶颈，因为查询在进程内串行。"

**追问 AF1-5. `get_compiled_graph()` 用了 `@lru_cache`，多个请求共享同一个编译后的图实例，有并发安全问题吗？**

**回答**："get_compiled_graph 用 @lru_cache 共享图实例。LangGraph 的 ainvoke 每次创建新的 state 副本——state 隔离由 ainvoke 内部保证，不需要额外加锁。但 checkpointer（MemorySaver）的内存操作可能有并发安全问题——它是 Python dict 存储，多线程读写需要锁。"

**追问 AF1-6. checkpointer 是内存实现，100 个会话同时写会怎样？有锁吗？**

**回答**："MemorySaver 100 个会话同时写：Python dict 的 GIL 保证单个操作原子性，但 checkpointer 的读写可能不是原子的——读-改-写之间可能被其他线程插入。低并发下没问题，高并发需要验证或换实现。"

**追问 AF1-7. 如果要横向扩展，多实例部署，checkpointer 的内存实现会有什么问题？**

**回答**："多实例部署时 MemorySaver 的问题：会话状态不共享——用户请求到实例 A，实例 A 存了 state；下一轮请求到实例 B，B 读不到 A 的 state。解决：换持久化 checkpointer（SqliteSaver/PostgresSaver），所有实例共享数据库。"

### AG. 成本控制

**Q AG1. 一次请求的 LLM token 成本大概多少？**

**回答**：
"正常路径约 2000-4000 token（输入+输出）。SQL 生成消耗最多因为 Prompt 里有 schema + 业务规则 + 上一轮问答。"

**追问 AG1-1. 哪个环节消耗 token 最多？SQL 生成还是报告总结？**

**回答**："SQL 生成消耗 token 最多——Prompt 里有方言 + schema_info（top-4 知识块约 800-1200 token）+ evidence（业务规则约 300 token）+ question + previous_step_results。输入约 1500-2000 token，输出约 200-500 token（SQL + reasoning）。"

**追问 AG1-2. RAG 召回 top-4 知识块大概多少 token？**

**回答**："RAG 召回 top-4 知识块约 800-1200 token。每个 chunk 约 200-300 token（一个表的字段说明 + JOIN 模板）。"

**追问 AG1-3. 多轮对话只带上一轮，比带全量历史省多少 token？**

**回答**："多轮只带上一轮比带全量历史省：上一轮约 500 token（question + SQL + answer），全量 N 轮历史约 500*N token。10 轮对话能省 4500 token。"

**追问 AG1-4. `execute_sql` 工具最多回传 20 行给 LLM，为什么截断？截断多少合适？**

**回答**："execute_sql 工具最多回传 20 行（MAX_PREVIEW_ROWS=20）给 LLM。截断因为千行结果打爆 LLM 上下文窗口。20 行通常够 LLM 总结趋势和关键数据。截断后如果数据不完整，LLM 会在答案里说'显示前 20 条'。"

**追问 AG1-5. 意图判断先用关键词启发式，能省多少 LLM 调用？**

**回答**："意图判断关键词启发式省多少：闲聊问题（如'你好''谢谢'）不需要调 LLM——省 1 次调用约 200-500 token。如果 30% 的请求是闲聊，省 30% 的意图分类成本。"

**追问 AG1-6. 如果用户问的问题很长（1000 字），API 层有长度限制吗？**

**回答**："用户问题长度限制在 API 层——SqlRequest 模型的 question 字段有 Pydantic 校验（max_length=1000）。超过 1000 字符返回 422 错误。"

> **代码锚点**：`app/tools/execute_sql.py:MAX_PREVIEW_ROWS`、`app/api/sql.py:SqlRequest`、`app/llm/client.py`

### AH. 性能优化方向

**Q AH1. 如果要优化这个项目的性能，你会从哪些方面入手？**

**回答**：
"优先级：① 向量索引预热；② 意图分类短路更多场景；③ SQL 生成结果缓存；④ MySQL 慢查询监控。"

**追问 AH1-1. LLM 调用串行 → 并行？哪些环节可以并行？**

**回答**："LLM 调用串行→并行：意图分类和 schema_recall 理论上可以并行（两者不依赖），但 LangGraph 的条件边依赖 intent 结果——如果分类是 CHAT 就不需要检索。所以并行要改图结构：intent 和 schema_recall 并行执行，intent 是 CHAT 时丢弃检索结果。复杂度增加收益有限。"

**追问 AH1-2. RAG 检索可以缓存吗？相同问题的检索结果缓存合理吗？**

**回答**："RAG 检索缓存：相同问题的检索结果缓存合理——知识库不频繁变更。可以用 LRU cache 缓存 (question -> chunks) 映射。但要注意缓存失效——知识库更新时清缓存。"

**追问 AH1-3. SQL 生成结果可以缓存吗？相同问题+相同 schema 缓存合理吗？**

**回答**："SQL 生成结果缓存：相同问题+相同 schema 缓存合理。但难度在于'相同问题'的判定——语义相同但字面不同的问题（如'销售额最高的商品'和'什么商品卖得最好'）应该命中缓存。需要语义级别的缓存键。"

**追问 AH1-4. 向量索引构建可以预热吗？首次请求慢的问题怎么解决？**

**回答**："向量索引预热：首次请求慢因为 ensure_indexed() 要加载知识文件切片向量化。可以在 lifespan 启动时预热——init_pool 之后调 ensure_indexed()。这样首次请求不需要等索引构建。"

**追问 AH1-5. MySQL 查询可以做慢查询监控吗？怎么加？**

**回答**："MySQL 慢查询监控：aiomysql 的 execute() 可以加耗时统计——记录 SQL + 耗时，超过阈值（如 1 秒）记 warning 日志。也可以用 MySQL 的 slow_query_log。"

**追问 AH1-6. 如果 Chroma 查询成为瓶颈，换 Milvus 能解决什么？**

**回答**："Chroma 查询成为瓶颈换 Milvus：Milvus 是独立服务，查询在独立进程，不占应用进程资源。但部署复杂度增加。在这个项目规模（几十个 chunk）Chroma 不会成为瓶颈。"

### AI. 加新表

**Q AI1. 如果业务加了一张新表（比如 `coupons` 优惠券表），需要改哪些地方？**

**回答**：
"只改知识库 md 文件——在 data/knowledge/schema/ 的 md 里加一个 ## 表名 小节。重启后 RAG 自动重建索引。不需要改代码。"

**追问 AI1-1. 知识库的 md 文件要加什么？加在哪个目录？**

**回答**："在 data/knowledge/schema/ecommerce.md 里加一个 ## coupons 小节，写明表名、字段、类型、业务含义。如果有业务规则，在 data/knowledge/business/ 里加一个 md 文件。"

**追问 AI1-2. 需要改代码吗？为什么不需要？**

**回答**："不需要改代码。因为知识加载是动态的——documents.py 的 load_knowledge_chunks() 遍历 data/knowledge/ 目录下所有 md 文件。新文件自动被加载。"

**追问 AI1-3. 重启后 RAG 怎么自动认识新表的？`ensure_indexed` 怎么做的？**

**回答**："重启后 ensure_indexed() 检查 Chroma 里有没有数据。如果有旧索引，新表的知识块会被加载但不会自动写入——因为 ensure_indexed 检查的是'有没有数据'而不是'数据是不是最新'。需要设 RAG_FORCE_REBUILD=True 强制重建，或者删除 data/chroma/ 目录。"

**追问 AI1-4. 如果不重启，能热更新知识库吗？现在为什么不行？**

**回答**："不重启不能热更新——因为 ensure_indexed() 只在首次调用时执行，后续请求跳过。get_retriever() 是 lazy singleton，首次创建后不会重新初始化。"

**追问 AI1-5. 如果要实现热更新，你会怎么设计？文件监听 + 增量索引？**

**回答**："热更新设计：用 watchdog 监听 data/knowledge/ 目录变更，变更后调 ensure_indexed(force=True) 增量索引新文件。chunk id 是稳定的（文件路径+小节序号），所以增量索引只添加新 chunk 不影响旧的。"

**追问 AI1-6. 新表加了之后，旧知识块的 chunk id 会变吗？向量需要全部重建吗？**

**回答**："新表加了之后旧知识块的 chunk id 不会变——id 是'文件路径+小节序号'，新表是新文件或新小节，不影响已有 id。向量不需要全部重建，只需要向量化新 chunk。但当前 ensure_indexed 不支持增量——它是全量的。改进项是支持增量索引。"

> **代码锚点**：`app/rag/documents.py:load_knowledge_chunks`、`app/rag/vector_store.py:ensure_indexed`

### AJ. 加新工具

**Q AJ1. 如果要给 LLM 加一个新工具（比如 `search_history` 查历史问答），怎么加？**

**回答**：
"三步：① 在 app/tools/ 里写新工具函数，用 @tool 装饰器标注；② 在 graph.py 的 _decide_tools() 里加到 bind_tools 列表；③ 如果工具返回的知识要 merge 到 state，在 nodes.py 的 tool_call_node 里处理。"

**回答**："新工具写在 app/tools/ 新文件里。用 @tool 装饰器标注——LangChain 会把函数签名 + docstring 转成 JSON Schema 给 LLM。"

**追问 AJ1-2. 怎么注册到 tool_call_node 的 bind_tools 列表里？**

**回答**："在 graph.py 的 _decide_tools() 函数里，把新工具加到 bind_tools 的列表：chat.bind_tools([search_schema_tool, execute_sql_tool, new_tool])。"

**追问 AJ1-3. 工具的 docstring 有什么要求？为什么要写得正式？**

**回答**："docstring 要求：写清参数含义、返回格式、什么场景该用。因为 docstring 就是 LLM 看的'工具说明书'——写得清楚 LLM 才能在正确场景选择正确工具。"

**追问 AJ1-4. `MAX_TOOL_CALLS_PER_TURN` 需要调大吗？新工具和现有两个工具有冲突吗？**

**回答**："MAX_TOOL_CALLS_PER_TURN 一般不需要调大——3 次够用。新工具和现有两个工具不冲突——工具之间是独立的，LLM 选择哪个取决于问题。如果新工具和 search_schema 功能重叠（如两个都是检索），LLM 可能选错，需要把 docstring 写得区分度高。"

**追问 AJ1-5. 如果新工具是异步的外部 HTTP 调用，超时怎么控制？**

**回答**："异步外部 HTTP 调用的超时：在工具函数内部用 httpx.AsyncClient(timeout=10) 控制超时。工具超时后返回 JSON {error: 'timeout'}，不抛异常。"

**追问 AJ1-6. 如果新工具需要写操作（比如 `insert_data`），安全边界怎么设计？你同意加吗？**

**回答**："写操作工具（insert_data）的安全边界：我不建议加。理由是 execute_sql 工具的设计是'校验在连接之前'，写操作的风险面太大。如果必须加：独立工具（不走 sqlglot 因为 sqlglot 拦写操作）、独立数据库连接池（读写分离）、独立审批流程。安全边界在'哪些表可写、什么 WHERE 条件下可写'。"

### AL. 换持久化方案

**Q AL1. 如果 checkpointer 从 MemorySaver 换成数据库持久化，怎么改？**

**回答**：
"改 app/agent/graph.py 的 get_compiled_graph()——把 MemorySaver() 换成 SqliteSaver() 或 PostgresSaver()。改动面是一个文件一行代码。"

**追问 AL1-1. LangGraph 提供了哪些 checkpointer 实现？**

**回答**："LangGraph 提供的 checkpointer 实现：MemorySaver（内存）、SqliteSaver（SQLite 文件）、PostgresSaver（PostgreSQL）。都是 BaseCheckpointSaver 的子类。"

**追问 AL1-2. 改动面有多大？只改一个文件吗？**

**回答**："改动面是一个文件——get_compiled_graph() 里 MemorySaver() 那一行换成新实现。图编译逻辑不变。"

**追问 AL1-3. `get_compiled_graph()` 用了 `@lru_cache`，换了 checkpointer 需要清缓存吗？**

**回答**："@lru_cache 缓存了编译后的图。换 checkpointer 后需要清缓存——functools.lru_cache 对象有 cache_clear() 方法。或者重启服务。生产环境建议不用 lru_cache，每次编译开销不大。"

**追问 AL1-4. 多实例部署时，checkpointer 存数据库能解决会话共享吗？**

**回答**："多实例部署时 checkpointer 存数据库解决会话共享——所有实例连同一个 PostgresSaver，读写同一个 checkpoints 表。thread_id（conversation_id）隔离保证不同会话不串。"

**追问 AL1-5. 持久化 checkpointer 会不会成为性能瓶颈？每次 ainvoke 都要读写数据库？**

**回答**："持久化 checkpointer 的性能：每次 ainvoke 要读写数据库——ainvoke 开始时读 checkpointer 恢复 state，结束时写 checkpointer 存 state。对于多轮对话这是必要的。优化是用连接池 + 异步 IO（PostgresSaver 支持 async）。"

**追问 AL1-6. 会话数据怎么清理？TTL 设多少合理？**

**回答**："会话清理：checkpointer 会累积历史快照。清理策略：按 TTL（如 7 天）定期删除旧快照。或按数量限制（每个 thread_id 最多存 N 轮）。MemorySaver 重启即清，持久化版本需要主动清理。"

> **代码锚点**：`app/agent/graph.py:get_compiled_graph`

### AM. SQL 自动修正重试

**Q AM1. 如果 SQL 执行报错，你想让系统自动修正 SQL 再试，怎么设计？**

**回答**：
"在 sql_execute_node 内部加重试逻辑：执行失败后把 MySQL 错误信息 + 原 SQL 喂回 LLM 生成修正版，上限 2 次防循环。"

**追问 AM1-1. 重试逻辑放在哪个节点？sql_execute_node 内部还是新节点？**

**回答**："重试逻辑放在 sql_execute_node 内部，不是新节点。因为重试需要访问 SQL 生成能力——如果放新节点要加条件边回 sql_generate，复杂度增加。放在 sql_execute_node 内部可以直接调 Text2SqlGenerator.agenerate() 重新生成。"

**追问 AM1-2. 错误信息怎么传给 LLM？MySQL 报错原文直接喂还是有脱敏？**

**回答**："错误信息传给 LLM：MySQL 报错原文直接喂——但只取关键信息（如 'Unknown column xxx in field list'），不带完整堆栈。不做脱敏因为 MySQL 错误信息不含敏感数据，只含表名/列名（这些 LLM 本来就知道）。"

**追问 AM1-3. 重试上限设多少次？为什么？防止什么？**

**回答**："重试上限 2 次。防止无限循环——LLM 可能反复生成同样的错误 SQL。2 次后还是失败就写 error 终止。"

**追问 AM1-4. 不同类型的错误（语法错/列名错/权限错/超时）重试策略一样吗？**

**回答**："不同错误重试策略不同：语法错（syntax error）→ 可以重试（LLM 修正语法）；列名错（Unknown column）→ 可以重试（LLM 换正确列名）；权限错（Access denied）→ 不重试（重试也没用）；超时（Lock wait timeout）→ 不重试（可能死锁）。需要先做错误分类。"

**追问 AM1-5. 重试失败后用户看到什么？有兜底文案吗？**

**回答**："重试失败后用户看到：error 字段有完整错误链（原始 SQL + 错误信息 + 修正尝试 + 最终失败原因）。兜底文案'查询执行失败，请尝试换一种问法'。"

**追问 AM1-6. 这个功能会不会增加安全风险？LLM 可能利用错误信息探测表结构？**

**回答**："安全风险：LLM 可能利用错误信息探测表结构——如故意生成错误的列名，从'Unknown column xxx'的报错推断哪些列存在。防御：限制重试次数（2 次），且 sqlglot 校验仍然生效——修正后的 SQL 也要过校验。readonly 账号保证即使探测到表结构也不能写。"

> **代码锚点**：`app/agent/nodes.py:sql_execute_node`、`app/agent/text2sql.py`

### AN. 权限控制方案

**Q AN1. 如果要加数据权限（不同用户只能看自己部门的订单），怎么设计？**

**回答**：
"在 SQL 生成层注入用户权限信息——Prompt 里加规则'WHERE 必须包含 department_id = 用户的部门'，sqlglot 检查 SQL 是否包含权限过滤。"

**追问 AN1-1. 在 SQL 生成层加 `WHERE department = ?` 还是查询后过滤？哪个更好？**

**回答**："在 SQL 生成层加 WHERE 比查询后过滤好。因为查询后过滤需要先查出全量数据再过滤——数据量大时性能差且有泄露风险（中间结果包含其他部门数据）。SQL 层加 WHERE 让数据库做过滤，只返回有权限的数据。"

**追问 AN1-2. 如果在 SQL 层加，Prompt 怎么注入用户权限信息？**

**回答**："Prompt 注入：在 new_sql_generate.txt 里加一个 {user_permission} 槽位，内容如'当前用户属于部门 X，所有查询必须包含 WHERE department_id = X'。build_turn_input 时从用户 session 取部门信息注入。"

**追问 AN1-3. 如果用户问"所有订单的销售额"，但只有本部门权限，系统应该怎么回答？**

**回答**："用户问'所有订单的销售额'但只有本部门权限：系统应该只返回本部门的销售额，并在答案里说明'以下为您部门的数据'。Prompt 规则强制 LLM 在 WHERE 里加部门过滤。"

**追问 AN1-4. 行级权限和列级权限分别怎么实现？**

**回答**："行级权限：在 SQL 里加 WHERE 条件（如 department_id = X）。列级权限：在 SELECT 里限制列（如不允许 SELECT password 列）。列级更难——需要 sqlglot 解析 SELECT 的列列表检查有没有禁列。行级相对简单。"

**追问 AN1-5. sqlglot 校验能帮忙做权限检查吗？还是需要在应用层做？**

**回答**："sqlglot 能帮忙做权限检查——解析 AST 后检查 WHERE 子句里有没有包含 department_id 条件。但更可靠的是在应用层做：sql_generate 后检查 AST 里的 WHERE 条件。sqlglot 提供 AST 遍历能力，可以检查 WHERE 节点的内容。"

**追问 AN1-6. 多租户场景下，不同租户的 schema 不同，RAG 怎么处理？**

**回答**："多租户场景不同 schema：RAG 知识库按租户分目录——data/knowledge/{tenant_id}/schema/。retriever 初始化时按 tenant_id 加载对应知识库。Chroma 按 tenant_id 分 collection。Prompt 里注入对应租户的表结构。"

> **代码锚点**：`app/prompts/new_sql_generate.txt`、`app/security/sql_validator.py`

### AO. 评估体系方案

**Q AO1. 怎么评估 Text-to-SQL 的准确率？**

**回答**：
"方法论：准备标注题目集，每条有标准 SQL 或标准结果集，跑完比对执行结果。规模先做 50 条覆盖 5 类场景。"

**追问 AO1-1. 评估集怎么构建？需要多少条标注题目？**

**回答**："评估集构建：50 条标注题目，覆盖 5 类场景：销售额类、极值类、聚合均值类、分组维度类、多轮追问类。每条有标准 SQL 或标准结果集。"

**追问 AO1-2. 比对 SQL 文本还是比对执行结果？为什么？**

**回答**："比对执行结果比比对 SQL 文本好。因为同一语义的 SQL 有多种写法——SELECT a FROM t 和 SELECT a as x FROM t 语义相同但文本不同。比对执行结果（行数据）更公平。"

**追问 AO1-3. 同一语义的 SQL 有多种写法，怎么判定等价？**

**回答**："SQL 等价判定：用 sqlglot 的 normalize 功能——把两个 SQL 都标准化（列名小写、去别名、排序 JOIN），然后比对 AST 结构。或者直接比对执行结果集（排序后比较行数据）。"

**追问 AO1-4. RAG 检索质量怎么单独评估？recall@K 怎么算？**

**回答**："RAG 检索质量评估：recall@K——准备'(问题, 应召回的 chunk id)'标注对，跑 recall 后检查 top-K 里有没有应召回的 chunk。K 用项目配置的 4。"

**追问 AO1-5. 评估集要不要定期更新？业务变更后旧题目还有效吗？**

**回答**："评估集要定期更新——业务变更后旧题目可能失效（如表结构变了、业务规则变了）。每次知识库更新后跑评估集回归。旧题目如果不再适用就淘汰，加新题目覆盖新场景。"

**追问 AO1-6. 有没有自动化的回归测试方案？每次改 Prompt 后自动跑评估集？**

**回答**："自动化回归：CI/CD 里加一个 job——每次改 Prompt 或知识库后自动跑评估集，输出准确率指标。准确率下降超过阈值（如 5%）阻断部署。用 pytest 的参数化功能实现。"

**Q AQ1. 回顾你的设计决策，哪些你觉得做得好？**

**回答**："CDN 单文件前端不后悔。什么场景下想重构：产品要求用户登录 + 多会话历史 + 离线消息 + 富文本输入——这些需要状态管理和组件化，CDN 方案不够用。但面试场景下 CDN 方案是最优解——复杂度预算花在后端。"

### AR. 深度理解复盘

**Q AR1. 做完这个项目，你对 LLM 应用开发的理解有什么变化？**

**回答**：
"之前以为 LLM 应用是'调 API'，做完后理解到核心是'让不可靠的 LLM 在工程框架内可靠地工作'。"

**追问 AR1-1. 之前对 LLM 的认知是什么？做完之后有什么改变？**

**回答**："之前对 LLM 的认知：一个强大的 API，输入文字返回文字。做完后的改变：LLM 是'认知引擎'——擅长理解和生成但不可靠、有幻觉、可能被诱导。工程的价值在于用框架约束和引导它。"

**追问 AR1-2. 你觉得 LLM 应用开发的核心难点是什么？不是写代码，是什么？**

**回答**："核心难点不是写代码，是'Prompt 工程 + 安全边界 + 降级策略'。Prompt 是 LLM 应用的'第一层代码'——写得好不好直接决定输出质量。安全边界是工程能力的体现——不能指望 LLM 自觉。降级策略是可靠性的保证——LLM 挂了系统不能白屏。"

**追问 AR1-3. "Prompt 工程"你怎么看？它是软件工程还是手艺活？**

**回答**："Prompt 工程是软件工程和手艺活的结合。框架化部分（模板、槽位、规则）是软件工程——可以 code review、可以测试。调优部分（措辞、示例、顺序）是手艺活——需要试错和经验。两者都需要。"

**追问 AR1-4. RAG 的价值你一开始就理解了吗？还是做的过程中才意识到的？**

**回答**："RAG 的价值是做的过程中意识到的。一开始以为 5 张表全塞 Prompt 就行，做的时候发现：知识按自然边界切片、带类型标签、按语义召回——这些结构在表数量增长时才有收益。但'为规模化预留正确结构'本身就是工程能力。"

**追问 AR1-5. 你对 Agent 的"自主性"和"可控性"的权衡怎么看？**

**回答**："Agent 的自主性和可控性是 trade-off：自主性高（ReAct 循环）能处理更复杂的任务但不可控、不安全。可控性高（确定性流程图）安全可测试但灵活性低。我的选择是可控性优先——安全要求（SQL 只读）必须由代码保证。自主性用在刀刃上（tool_call 的工具选择）。"

**追问 AR1-6. 如果面试官问你"Agent 和传统后端系统的本质区别是什么"，你怎么回答？**

**回答**："Agent 和传统后端系统的本质区别：传统后端处理确定性逻辑（if-else、数据库 CRUD），Agent 处理模糊性逻辑（自然语言理解、内容生成）。传统后端的可靠性靠事务和幂等，Agent 的可靠性靠多层校验和降级。传统后端测试验证逻辑正确性，Agent 测试验证编排逻辑和降级行为。"

### AS. 与其他项目对比

**Q AS1. 这个 AI 项目和你的 Java 高并发项目，在设计思维上有什么不同？**

**回答**：
"Java 项目处理可控的确定性逻辑，AI 项目处理不可控的模糊性逻辑。但两者的共同点是'把不可靠的外部依赖用工程手段变可靠'。"

**回答**："Java 项目处理的是确定性逻辑——接口请求→查缓存→查数据库→扣库存→下单。每一步行为可预测。AI 项目处理的是模糊性逻辑——用户问什么不确定、LLM 生成什么不确定、生成对不对不确定。工程手段是约束和校验。"

**追问 AS1-2. Java 项目里的限流熔断和这个项目里的多层安全防线，设计思想上有共同点吗？**

**回答**："Java 的限流熔断和 AI 的多层安全防线设计思想有共同点：都是'承认外部依赖不可靠，用多层防护降低风险'。Java 里下游服务可能超时→限流熔断兜底；AI 里 LLM 可能生成恶意 SQL→sqlglot + readonly 账号兜底。"

**追问 AS1-3. 两个项目里"测试"的意义一样吗？Java 测逻辑正确性，AI 项目测什么？**

**回答**："测试意义不同：Java 测逻辑正确性（给定输入期望输出——确定性）。AI 项目测编排逻辑（节点顺序对不对、条件边路由对不对）和降级行为（LLM 返回垃圾时系统是否优雅处理）——LLM 本身的正确性不可测。"

**追问 AS1-4. 如果把这个项目的 LangGraph 换成 Java 的状态机框架（如 Spring StateMachine），可行吗？代价是什么？**

**回答**："LangGraph 换 Spring StateMachine 可行：StateGraph 的节点=状态机的状态，条件边=状态转移条件。代价：① LangGraph 的 astream 流式输出要手写；② checkpointer 状态持久化要手写；③ /api/graph/structure 图结构自省要手写。LangGraph 这些都是免费的。另外 Java 生态的 AI 集成不如 Python（LangChain 生态在 Python）。"

## 九、反套路问题（区分自己做的还是抄的）

> 目标：通过细节追问，区分"自己做的"和"照着教程跑的"。

### AT. 代码细节追问（只有写过才知道）

**Q AT1. `tool_call_node` 里判定工具成功还是失败，看的是什么字段？**

**回答**：
"看工具返回 JSON 里的 error 字段——有 error 就是失败，没有就是成功。不看有没有抛异常。"

**追问 AT1-1. 为什么不看有没有抛异常？**

**回答**："不看异常因为工具设计是'把 sqlglot 拒绝以正常返回回传'——执行_sql 工具内部 catch SqlValidationError 后返回 {error: '...'}，不抛异常。如果看异常就会漏掉这种'正常返回的失败'。"

**追问 AT1-2. "没有异常"等于"成功"吗？什么情况下不是？**

**回答**："没有异常不等于成功。execute_sql 校验失败时不抛异常而是返回 JSON {error: 'Only SELECT is allowed'}——没有异常但工具执行失败了。所以必须解析 JSON 的 error 字段。"

**Q AT2. `build_turn_input()` 里重置了哪些标志位？**

**回答**：
"重置 4 个：tool_called=False、schema_needs_tool=False、tool_results=[]、tool_error=''。"

**追问 AT2-1. 为什么要重置？不重置会怎样？**

**回答**："重置因为 checkpointer 会把上一轮的 State 完整带进本轮。不重置的话上一轮的 tool_called=True 会让条件边的 not tool_called 判定永远 False，工具路径永远不触发。"

**追问 AT2-2. 这些标志位是哪几个？能说出字段名吗？**

**回答**："4 个标志位：tool_called（是否调了工具）、schema_needs_tool（是否需要工具兜底）、tool_results（工具结果列表）、tool_error（工具错误信息）。"

**追问 AT2-3. 如果将来加了一个新标志位忘了重置，会出什么问题？**

**回答**："如果将来加了新标志位忘了重置，会出现类似的'跨轮残留'问题——上一轮的值影响本轮的条件判定。预防：在 build_turn_input 里加注释提醒'新增跨轮标志位时在此重置'。"

**Q AT3. `_route_after_recall` 条件里为什么有 `not tool_called`？**

**回答**：
"防环保护——保证工具路径每轮最多触发一次。"

**追问 AT3-1. 去掉这个条件会怎样？会导致什么死循环？**

**回答**："去掉 not tool_called 会导致死循环：tool_call 执行后如果出边回 schema_recall，schema_recall 又判定 schema_needs_tool=True → 再进 tool_call → 无限循环。有 not tool_called 后，第一次 tool_call 后 tool_called=True，条件不再满足，不会再次进入。"

**追问 AT3-2. 这个条件是防什么场景的？**

**回答**："这个条件防的场景：LLM 第一次检索没用对关键词，tool_call 执行后理论上想再检索一次。但我的设计是单轮决策——tool_call 后直接进 sql_generate，不回边。not tool_called 是结构性保证。"

**Q AT4. `execute_sql` 工具最多回传几行给 LLM？这个限制在哪定义的？**

**回答**：
"MAX_PREVIEW_ROWS=20，在 app/tools/execute_sql.py 里定义。"

**追问 AT4-1. 常量名叫什么？**

**回答**："常量名叫 MAX_PREVIEW_ROWS，值为 20。"

**追问 AT4-2. 为什么截断？不截断会怎样？**

**回答**："截断因为千行结果打爆 LLM 上下文窗口。20 行通常够 LLM 总结趋势和关键数据。"

**追问 AT4-3. 截断后 LLM 看到的是部分数据，报告会不会不准确？**

**回答**："截断后报告可能不准确——如果查询返回 1000 行但 LLM 只看 20 行，总结可能不完整。应对：LLM 在答案里说'显示前 20 条，共 1000 条'。用户可以换问法（如'按销售额排序前 10'）缩小结果集。"

**Q AT5. 知识库切片时，如果一个 `##` 小节超过 `rag_chunk_size`（400字符），会怎么处理？**

**回答**：
"递归字符切分。如果 ## 下的内容超过 rag_chunk_size（400 字符），用 RecursiveCharacterTextSplitter 按 overlap=60 切。"

**追问 AT5-1. 是直接截断还是递归切分？**

**回答**："递归切分，不是直接截断。RecursiveCharacterTextSplitter 先按段落分，段落太长按句子分，句子太长按字符分。"

**追问 AT5-2. 切分时 `overlap` 是多少？为什么需要 overlap？**

**回答**："overlap=60 字符。overlap 是切分时相邻 chunk 之间重叠 60 字符——保证切分边界处不丢失上下文。比如一个字段说明被切分到两个 chunk，overlap 保证两个 chunk 都包含边界附近的文字。"

**Q AT6. `_HashEmbedding` 的向量维度是多少？怎么生成的？**

**回答**："64 维，用 SHA-256 哈希生成。"

**追问 AT6-1. 用的是什么哈希算法？**

**回答**："SHA-256 哈希算法。对文本做 SHA-256 得到 256 位哈希值，取前 64 字节映射成 64 维浮点向量。"

### AU. "为什么这么做"追问

> 照着抄的答不出来——只有理解设计决策的原因才能回答。

**Q AU1. 为什么 SQL 生成的 Prompt 里要分 `schema_info` 和 `evidence` 两个槽，不能合在一起吗？**

**回答**："因为职责不同：schema 回答'能用什么表/字段'，evidence 回答'怎么算'。"

**追问 AU1-1. 分开和不分开对 LLM 生成质量有什么影响？**

**回答**："分开让 LLM 看到结构化的知识分类——表结构和业务规则在 Prompt 里分开排列，LLM 更容易区分'这是表结构'和'这是业务口径'。不分开可能导致 LLM 混淆表结构信息和业务规则。"

**追问 AU1-2. 你试过合在一起吗？效果变差了吗？**

**回答**："没试过合在一起。但从 Prompt 工程的角度，结构化分类通常比混在一起效果好——LLM 的注意力机制对有结构的信息处理更好。"

**Q AU2. 为什么意图判断要用关键词启发式，不直接全部交给 LLM？**

**回答**："省成本、降延迟、降风险。"

**追问 AU2-1. 省一次 LLM 调用能省多少成本？**

**回答**："省一次 LLM 调用约省 200-500 token + 500ms 延迟。如果 30% 的请求是闲聊，省 30% 的意图分类成本。"

**追问 AU2-2. 关键词列表是谁定的？怎么决定加哪些词？**

**回答**："关键词列表我定的。怎么决定加哪些词：分析常见闲聊场景——打招呼（你好/hello/hi）、感谢（谢谢/感谢）、身份询问（你是谁/你能做什么）。这些词出现频率高且意图明确。"

---

**Q AU3. 为什么 tool_call_node 每轮只进一次，不允许多次绕行？**

**回答**："结构性防环。"

**追问 AU3-1. 如果 LLM 第一次检索没用对关键词，想再检索一次怎么办？**

**回答**："当前不支持。设计是单轮决策：LLM 在 tool_call 做一次工具选择，执行后直接进 sql_generate。如果 sql_generate 的兜底（全量文档）还不够，生成失败就返回 error。"

**追问 AU3-2. "每轮只进一次"是靠什么保证的？条件边的标志位？**

**回答**："每轮只进一次靠条件边的 not tool_called 标志位保证——tool_call 执行后 tool_called=True，条件不再满足。另外 build_turn_input 每轮入口重置 tool_called=False。"

---

**Q AU4. 为什么 `execute_sql` 工具校验失败返回 JSON 而不是抛异常？**

**回答**："让 LLM 能读到错误信息，且不中断图。"

**追问 AU4-1. 如果抛异常，tool_call_node 会怎样？**

**回答**："如果抛异常，tool_call_node 的 _interpret_tool_output 会 catch 异常标记失败——但 LLM 看不到失败原因（异常被 catch 后没有传给 LLM）。"

**追问 AU4-2. 返回 JSON 让 LLM 能读到错误信息，这有什么好处？**

**回答**："返回 JSON 让 LLM 能读到 error 字段——JSON 就是文本，LLM 读得懂。理论上 LLM 可以利用错误信息调整行为（虽然当前没有修正机制）。"

**追问 AU4-3. LLM 读了错误信息后有机会修正吗？现在有修正机制吗？**

**回答**："LLM 读了错误信息后当前没有修正机制——工具结果写进 state 后图继续走 sql_generate，LLM 基于已有知识重新生成。改进项是加'读到工具失败后修正 SQL'的回边。"

**Q AV2. 你在写 Prompt 模板时，有没有遇到过 LLM 不遵守规则的情况？**

**回答**："遇到过。主要是 markdown 围栏和编造表名。"

**追问 AV2-1. 比如生成带 markdown 围栏的 SQL？怎么处理的？**

**回答**："markdown 围栏：LLM 生成 \`\`\`sql ... \`\`\` 格式。处理：with_structured_output(SqlGeneration) 强制结构化输出，sql 字段保证没有围栏。在引入结构化输出之前确实遇到过，引入后没再出现。"

**追问 AV2-2. 比如生成了不存在的表名？怎么处理的？**

**回答**："编造表名：LLM 生成了不存在的表。处理：Prompt 规则'只准用 SCHEMA 槽里的表'。但如果 RAG 召回为空且兜底也没覆盖到，LLM 还是会编造。sqlglot 不做表名校验——这是改进项（连 information_schema 检查表名存在性）。"

**追问 AV2-3. 你是怎么迭代 Prompt 的？拿错例回填？**

**回答**："迭代方式：拿错例回填——生成错一次就在 Prompt 规则区加一条。比如发现 LLM 用了分号结尾，加规则'禁止以分号结尾'。"

**追问 AV2-4. 迭代了几轮？最有用的一条规则是哪条？**

**回答**："迭代了约 3-4 轮。最有用的一条规则是'只准使用 SCHEMA 槽里的表和字段，不允许发明'——这从源头压缩了幻觉空间。"

**Q AV3. 测试 99 个用例，你写测试时有没有遇到"测试通过了但其实逻辑有 bug"的情况？**

**回答**："遇到过。主要是 stub 的返回值太简单，覆盖了 bug 而不是暴露了 bug。"

**追问 AV3-1. 怎么发现测试本身有问题的？**

**回答**："发现测试本身有问题：_StubT2S 总是返回 'SELECT 1'，测试断言 SQL 非空就通过——但真实 LLM 返回空 SQL 时 sql_execute_node 的处理逻辑没被测到。发现后加了 'SQL 为空时跳过执行' 的测试。"

**追问 AV3-2. 你怎么保证测试覆盖了关键路径？有没有遗漏的场景？**

**回答**："保证覆盖关键路径：① 每个条件边的每个分支都有测试（走工具/不走工具/闲聊直达）；② 异常路径有测试（LLM 超时、SQL 校验失败、MySQL 挂了）；③ 多轮对话有测试（上下文注入、会话隔离、标志位重置）。遗漏的场景：SQL 语法合法但语义错误（如表名对但列名错）——这种需要真实 LLM 才能测。"

### AW. 隐含知识追问

**Q AW1. `get_compiled_graph()` 用了 `@lru_cache`，这意味着图实例是全局单例。多个请求共享同一个图实例，AgentState 会被串改吗？**

**回答**："不会。LangGraph 的 ainvoke 每次创建新的 state 副本。"

**追问 AW1-1. LangGraph 的 ainvoke 是怎么保证 state 隔离的？每次 ainvoke 创建新的 state 副本吗？**

**回答**："LangGraph 的 ainvoke 内部：读取 input state → 创建 state 副本 → 在副本上执行节点 → 写 checkpointer → 返回最终 state。多个请求的 ainvoke 各自操作各自的 state 副本，互不干扰。"

**追问 AW1-2. 如果两个请求的 conversation_id 相同会怎样？是 bug 还是 feature？**

**回答**："如果两个请求的 conversation_id 相同：它们读同一个 checkpointer 快照——第二个请求可能读到第一个请求刚写入的 state（如果第一个还没完成）。这在同步场景下是 bug，在异步场景下取决于时序。实际使用中不同用户的 conversation_id 不同，不会冲突。"

**追问 AW1-3. checkpointer 的 thread_id 隔离是在哪一层做的？**

**回答**："thread_id 隔离在 checkpointer 层做——get_state(thread_id) 只返回该 thread 的快照。不同 thread_id 读不同快照。MemorySaver 内部用 dict 存储，key 是 thread_id。"

---

**Q AW2. `init_default_helpers()` 在 `main.py` 的 import 阶段就执行了，这意味着 helper 函数在模块加载时就注入了。如果有人在 import 之后修改了 helper，会生效吗？**

**回答**："helper 在模块加载时注入。如果 import 之后修改 helper，需要再调 set_helpers 才生效。"

**追问 AW2-1. 为什么在 import 阶段注入而不是在 lifespan 启动时注入？**

**回答**："在 import 阶段注入而不是 lifespan 启动时，是因为 main.py import 时 init_default_helpers() 被调用（它在模块顶部）。好处是：任何 import 了 graph.py 的模块都能直接用——不需要等 lifespan。坏处是：如果 config 没加载好（如 .env 没配），helper 可能初始化失败。但 init_default_helpers 只是注册函数引用，不执行——执行在节点调用时。"

**追问 AW2-2. 测试里 `set_helpers()` 是在 fixture 里调。fixture 的 autouse=True 保证了每个测试前都恢复。如果没有 autouse 会怎样？**

**回答**："测试里 set_helpers 在 fixture 里调。autouse=True 保证每个测试前都恢复 helpers。如果没有 autouse，前一个测试的 stub 会残留到下一个测试——test isolation 被破坏。conftest.py 的 _restore_helpers fixture autouse=True 保证隔离。"

**Q AW3. 项目的 `repository.py` 里有 Stats 类提供手工聚合查询，现在还在用吗？**

**回答**："被 LLM 生成的 SQL 替代了，但保留作为后备。"

**追问 AW3-1. 这些查询现在被 LLM 生成的 SQL 替代了吗？**

**回答**："这些查询现在被 LLM 生成的 SQL 替代了——sql_generate_node 生成的 SQL 和 Stats 类的查询覆盖相同的业务场景。"

**追问 AW3-2. 为什么还保留这个文件？是历史遗留还是有计划用途？**

**回答**："保留是因为：① 历史遗留——Phase 3 用手工查询验证流程，Phase 6+ 才用 LLM；② 后备方案——手工 SQL 100% 正确，LLM 生成的可能有幻觉，生产环境可以 fallback 到手工查询；③ 文档作用——Stats 类的查询就是业务口径的代码级文档。"

**追问 AW3-3. 如果保留，它和 LLM 生成的 SQL 有什么区别？哪个更可靠？**

**回答**："手工 SQL 更可靠——它是人写的、经过验证的。LLM 生成的 SQL 灵活但有风险。生产环境如果对准确率要求高，可以对高频问题预定义手工 SQL（Stats 类），低频问题用 LLM——hybrid 方案。"

### AX. 架构权衡追问

**Q AX1. 你说"LLM 做认知、代码做决策"，但 tool_call_node 里 LLM 决定了调什么工具，这不也是"决策"吗？**

**回答**："我的界定：'决策'是流程走向（走哪个节点），LLM 决定调什么工具是'认知'（在节点内做什么）。"

**追问 AX1-1. 你怎么界定"认知"和"决策"的边界？**

**回答**："认知和决策的边界：'接下来走哪个节点'是决策——由图的边决定，LLM 不参与。'节点内做什么'是认知——LLM 生成内容、选择工具。tool_call 节点里 LLM 选择调 search_schema 是认知（在节点内选择做什么），不是决策（节点执行完后的下一步由图边决定——进 sql_generate）。"

**追问 AX1-2. LLM 决定调 search_schema 和 LLM 决定写什么 SQL，性质上有什么不同？**

**回答**："LLM 决定调 search_schema 和决定写什么 SQL 的区别：前者是'选择信息来源'（选哪个工具获取知识），后者是'生成内容'（写 SQL）。但两者都是'在节点内做事'，不是'决定流程走向'。性质上都是认知。"

**追问 AX1-3. 如果 LLM 在 tool_call 里选了 execute_sql 直接查，跳过了 sql_generate，这算"决策"吗？**

**回答**："如果 LLM 在 tool_call 里选了 execute_sql 直接查——它跳过了 sql_generate。但这不是 LLM 决定流程走向——是 LLM 选择了一个工具，节点执行工具后图继续按固定边走 sql_generate。sql_generate 会消费 execute_sql 的结果（如果结果里有 chunks）。流程走向没变。"

---

**Q AX2. 你的四层安全防线，如果只能保留一层，你保留哪层？为什么？**

**回答**："保留 readonly 账号——最不可替代。"

**追问 AX2-1. 哪层"性价比"最高？**

**回答**："性价比最高的是 sqlglot AST 校验——它拦截了绝大多数恶意 SQL，且在建立数据库连接之前。但它的前提是代码正确（sqlglot 本身没 bug）。"

**追问 AX2-2. 哪层"最不可替代"？**

**回答**："最不可替代的是 readonly 账号——即使代码全被绕过（sqlglot 有 bug、Prompt 被注入、结构化输出失败），数据库账号本身没有写权限。它是物理限制不是代码限制。"

**追问 AX2-3. 去掉 Prompt 软约束会怎样？去掉 sqlglot 会怎样？去掉只读账号会怎样？**

**回答**："去掉 Prompt 软约束：LLM 可能生成更多格式错误的 SQL，但结构化输出和 sqlglot 还能兜底——SQL 质量下降但安全不受影响。去掉 sqlglot：只靠 Prompt 和 readonly——readonly 能防写但防不了 SLEEP（资源消耗）和大结果集。去掉 readonly：前 3 层都是代码，代码可能有 bug——一旦被绕过数据库就暴露了。纵深防御的意义就是任何单层失效都不导致事故。"

---

**Q AX3. 你的 RAG 三级兜底（RAG → 工具 → 全量文档），如果只能保留一级，你保留哪级？**

**回答**："保留全量文档——它保证 schema 槽永远不为空。但 RAG 的价值不在于现在而在于规模化。"

**追问 AX3-1. 为什么不直接用全量文档？RAG 的价值在哪？**

**回答**："不直接用全量文档是因为：现在 5 张表全量约 2000 token，50 张表可能 20000 token——上下文窗口放不下且注意力被稀释。RAG 让上下文长度不随表数量增长。"

**追问 AX3-2. 如果知识库只有 5 张表，全量文档够不够？RAG 是不是多余的？**

**回答**："如果知识库只有 5 张表，全量文档够用——RAG 确实是多余的。但 RAG 的价值是'为规模化预留正确结构'——知识按自然边界切片、带类型标签、按语义召回，这些结构在表数量增长时才显现收益。现在的 RAG 是'花小钱买保险'。"

**追问 AX3-3. 你说 RAG 是"为规模化预留的正确结构"，这个判断的依据是什么？**

**回答**："'为规模化预留正确结构'的依据：① 知识切片和检索逻辑已经写好——50 张表时不需要改代码，只需要加 md 文件；② RAG 让上下文长度不随表数量线性增长——50 张表时只放 top-4 相关块；③ 工具检索（search_schema）提供按需补充知识的能力——LLM 可以主动查缺失的信息。这三点在 5 张表时不显现，在 50 张表时是必需。"
